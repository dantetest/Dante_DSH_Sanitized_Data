# 05 · 付费与解锁规划：软件内购二维码 / 收款保障 / ICP 过渡（规划，不写产品代码）

> **状态**：规划文档 · 2026-10-21 · **未修改产品代码**
> **问题**：L2/DSH 检测形态下，如何确保能收到费？ICP 在办理中，希望做成"软件内购：弹二维码 → 扫码 → 付款 → 解锁"。
> **先读**：[商业化总览](monetization.md) · [离线授权](licensing.md) · [支付与发票](payment-invoice.md) · [免费版限制](free-tier.md) · [L2 规划](04-MCP-L2-Agent内检测-规划.md)
> **结论先行**：
> 1. **二维码只是入口，收款保障不靠二维码**：靠"合规商户通道 + 服务端订单/回调验签 + 付款后才签发签名授权 + 对账/发票/退款"。二维码截图、假页面、改本地文件都不能解锁。
> 2. **ICP 未下来前不能上线"自有域名直连微信/支付宝"的个人内购**（支付商户号/场景审核通常要求已备案域名与主体一致；且 ICP 备案≠支付资质，需法务/支付机构确认）。**现在**可走：对公转账+人工签发（企业客户）/ 合规平台卖"授权码"（个人早鸟）；**ICP+商户号下来后**再切"App 内 Native 扫码 → 自动解锁"。
> 3. 内购 UI 建议做成**一个入口、两种通道**：`静态购买码`（零外呼，现在可用）与 `Native 支付码`（ICP 后，自动解锁）；产品 UI 不变，只换二维码来源。
> 4. **零外呼口径（已确认）**：文件处理引擎保持零外呼；**购买/授权 UI 层**（控制台 WebView/DSH Host 插件/桌面外壳）只在用户主动点击时访问官方商业服务。二维码可由本地前端纯生成（静态购买码），B 模式由 UI 层建单/轮询/下载 license 后交给同源引擎导入；引擎不参与任何网络请求。口径统一为："文件处理全程本机；购买/授权仅在用户点击时联网。"
> 5. 分期投入：授权内核+免费版+内购入口 **9–15 人日**（不依赖资质）；商业服务 **15–20 人日**（已有设计，可并行）；ICP 后 Native 自动解锁增量 **3–5 人日**；总 **约 30–40 人日 + 资质审批关键路径**。

---

> **2026-10-21 本轮确认（已拍板）**：
> - **P1 接受**"用户点击时联网"的宿主/浏览器侧购买通道；文件处理引擎仍保持零外呼。
> - **P2 双模式全部预置、服务端切换**：A（静态购买码/授权码）与 B（Native 扫码自动解锁）同一客户端版本内置，B 默认休眠，ICP/商户号到位后只切服务端配置，无需重装/二次发版（详见 §2.3）。
> - **P3 主体/资料**：公司主体 **四川步络骞科技有限公司**；对公账户已有、域名已有、ICP 即将下来；银行/商户密钥等资料后续经安全渠道提供，代码侧只留占位接口（详见 §5.4）。
> - **P4 按建议**：首发版本（v1.2.0）带 licensing + 14 天试用 + 存量用户 1 年专业版保护；MCP/DSH 检测从该版本起纳入专业版，新用户试用后付费；v2.0 起全面按专业版收费。定价沿用 P6（专业版年付 ¥499、早鸟 ¥299 限量 300、买断 ¥999）。

## 0 直接回答："怎么确保我们能收到费？"

收款是一条**链**，任何一环断了都收不到/收不稳：

| 层 | 要解决的问题 | 做法（本产品落地） |
|---|---|---|
| 1 合规收款 | 钱进哪个账户、能不能开发票 | 企业主体 + 对公账户 + 微信/支付宝商户号（ICP 后）；过渡期对公转账/合规平台 |
| 2 订单与回调 | 用户付了钱，系统知道且只算一次 | 服务端建单；渠道异步回调**验签 + 金额核对 + 幂等**；支付状态以渠道为准 |
| 3 交付与授权 | 付了钱才给能力，且不能靠截图/改文件白嫖 | 付款后服务端**Ed25519 签名 license**；客户端内置公钥离线验签；绑定机器码/有效期/功能位 |
| 4 防绕过 | 本地软件无法绝对防破解 | 提高成本：签名授权、机器绑定、功能门禁在引擎、服务端换机控制、价格低+持续更新；**不承诺绝对防破解** |
| 5 对账/售后 | 收得准、退得掉、票能开 | 每日渠道账单对账；重复支付自动退款；7 天未签发可退；发票红冲；客服 runbook |

> 一句话：**先付款、后签发、签名授权解锁、渠道回调为准、每日对账**。内购二维码只是第 1 层入口。

## 1 先判断：ICP 办理中意味着什么

### 1.1 支付资质是独立于 ICP 的另一条链

| 事项 | 作用 | 与 ICP 的关系 | 现状（待确认） |
|---|---|---|---|
| 营业执照 / 对公账户 | 商户主体、结算 | 必须与 ICP 主体一致 | 已有/待确认 |
| 域名 ICP 备案 | 网站合法接入 + 支付场景材料 | 支付机构审核常见要求 | **办理中** |
| 微信支付商户号 / 支付宝企业账号签约 | 真正能收款 | 需备案域名/经营场景/类目 | 未就绪（推断） |
| 电子发票能力（税控/云开票） | 开票/红冲 | 独立 | 待确认 |
| 用户协议/隐私政策/EULA/退款政策 | 合规售卖 | 独立（法务审） | 待办 |
| 软件著作权（建议） | 维权/部分渠道 | 不阻塞 | 待办（1–3 月） |

> **重要**：ICP 备案 ≠ 支付许可 ≠ ICP 许可证。自营软件销售通常"备案 + 商户资质"起步，但"在线服务/会员"是否还需增值电信业务经营许可证（ICP 证）需按实际业务与属地通管局确认；**本规划不代替法务结论**。

### 1.2 现在能做 / 不能做

| 能做（不依赖资质） | 不能做（等资质） |
|---|---|
| 授权内核 W1（Ed25519/机器码/trial/门禁） | 自有域名 + 微信/支付宝**直连收款** |
| 免费版限额 W2 + MCP 授权门禁 | 面向个人消费者的**正式公开售卖页**（无备案域名场景） |
| 内购入口 UI（静态购买码/对公入口/授权导入） | 自动开票（税控/云开票未就绪时） |
| 商业服务骨架 + 沙箱联调（无真实收款） | 真实资金结算、退款原路退回 |
| 对公转账 + 合同 + 人工签发（企业/团队） | 个人收款码收经营性款项（**明确不做**） |
| 合规平台卖"授权码/卡密"（个人早鸟，平台代收） | 二次清算类聚合支付（合规风险，**不建议**） |

## 2 "软件内购"三种实现（推荐 A → B）

同一个弹窗 UI，背后三种通道；先上 A，ICP+商户号后升级 B。

| 模式 | 用户看到 | 技术 | 零外呼 | 现在可用 | 自动解锁 |
|---|---|---|---|---|---|
| **A 静态购买码（推荐先做）** | 弹窗二维码 → 手机扫码 → 手机浏览器/平台付款 → 回电脑导入授权/激活码 | 二维码由本地前端生成，内容=购买页 URL + 机器码/sku/来源参数；引擎不联网 | ✅ 完全保持 | ✅ 平台/对公先跑 | ❌（需回填授权，可做"我已完成支付"引导） |
| **B Native 支付码（ICP 后）** | 弹窗二维码（微信/支付宝 Native）→ 扫码付款 → 自动下载授权 → 解锁 | 软件外壳/DSH Host 插件在用户点击时调商业服务建单、轮询、安装 license；引擎仍不联网 | ⚠️ 引擎保持，但宿主侧新增"用户主动触发的官方商业服务访问" | ❌ 等商户号 | ✅ |
| **C 跳浏览器（最保守）** | 点"购买"打开系统浏览器购买页 | 现有设计（payment-invoice.md） | ✅ | ✅ | ❌（下载/导入） |

### 2.1 推荐路线

1. **现在（ICP 办理中）**：做 A。弹窗二维码指向"官方购买页（未来域名）或平台商品页（过渡）"；付款后按过渡方案发授权；同时保留对公转账/团队合同入口。
2. **ICP+商户号下来后**：做 B。保留 A 作为"扫码失败/企业采购"兜底；两者共用订单/授权服务。
3. **不做 C 单独入口**——C 作为 B 失败时的降级链接即可。

### 2.2 关于"零外呼"红线的明确口径

- 现状承诺（README/CONTRACT）：引擎零出站 socket、无账号、无遥测。
- A 方案完全保持该承诺：二维码不联网生成，付款在手机侧完成；**授权文件由用户导入**。
- B 方案必须改成两句话（需用户确认）：
  > "文件处理引擎全程零外呼；**购买/授权功能**仅在用户主动点击时访问官方商业服务（不涉及用户文件）。"
- 如果不接受改口径：只能做 A+C，**无法实现"扫码后自动解锁"**（自动解锁需要客户端读取支付结果并下载 license，必然有一次联网）。

### 2.3 双模式预置与切换（本轮确认：都预备，服务端切换）

**可以，而且推荐这样做**：首发版本就把 A/B 两套通道都做进客户端（B 默认休眠），ICP/商户号到位后只切服务端配置，**不需要重装/二次发版**。

- **一套 UI、两种通道**：`purchase.channel = static | native | mixed`（服务端配置）；`static` = 静态购买码/授权码（A，零外呼）；`native` = 微信/支付宝 Native（B，自动解锁）；`mixed` = 优先 native，失败回退 static。
- **联网位置**：B 的建单/轮询/下载 license 在"购买 UI 层"完成——控制台 WebView 浏览器 JS，或 DSH Host 插件/桌面外壳。**引擎进程仍零外呼**；控制台页面与引擎同源，购买页 JS 可直接调商业服务（商业服务需允许 `http://127.0.0.1:*` 的 CORS），拿到 license 后 POST 给同源引擎 `/api/license/import` 本地验签解锁。DSH 面板如无法直连引擎，由 Host 插件代理，或引导到控制台完成最后一步。
- **数据与授权兼容**：A/B 共用同一订单/授权模型（`orders`/`payments`/`licenses` schema 不变，只加 `payments.channel` 字段）；A 发出的卡密/授权码在 B 上线后继续有效；切换不影响已签发 license。
- **切换闸门（全部满足才切）**：① ICP 备案号下来；② 微信/支付宝商户号 + 应用签约；③ 回调域名 HTTPS 可达；④ 沙箱全链路通过；⑤ 真实小额支付/退款/开票演练通过；⑥ 用户协议/隐私/退款政策上线；⑦ 监控告警/对账 runbook 就绪。
- **灰度与回滚**：`channel=mixed, rollout=10% → 50% → 100%`；监控支付成功率、回调失败率、解锁失败率、退款率；异常时改回 `static`（<1 分钟生效，无需发版）。
- **兜底**：任何 native 失败（渠道维护/回调延迟/客户端网络异常）自动显示"改用授权码 / 对公转账"入口。

## 3 资金与授权链路（B 模式完整时序）

```
用户            本机（软件/DSH 面板）        商业服务（公网）             支付渠道
 │ 点「解锁专业版」 │                            │                        │
 │───────────────▶│ ① 建单（sku/机器码/来源）    │                        │
 │                │───────────────────────────▶│ 订单 pending            │
 │                │◀───────────────────────────│ 返回支付二维码/URL      │
 │ 扫码/付款       │ ② 显示二维码（本地渲染）      │                        │
 │──────────────────────────────────────────────────────────────────────▶│
 │                │                            │◀── ③ 异步回调（验签） ──│
 │                │                            │ 金额核对/幂等/订单 paid │
 │                │                            │ ④ 绑定机器码（一次性）   │
 │                │                            │ ⑤ 签发 license（Ed25519）│
 │                │◀───────────────────────────│ ⑥ 授权文件/下载 token   │
 │                │ ⑦ 本地验签 → 写入数据目录 → 热加载解锁                 │
 │                │ ⑧ 开票/对账/退款（后台）                              │
```

关键点（与 [payment-invoice.md](payment-invoice.md)、[licensing.md](licensing.md) 对齐）：

- 订单金额由**服务端 SKU 快照**计算（int 分）；回调核对 `amount/mchid/appid/trade_state`；
- `out_trade_no` 随机不可枚举；回调幂等（`transaction_id` 唯一）；同订单二次支付 → 退款队列，不重复签发；
- 绑定机器码与签发都在服务端；**签名器独立进程/主机，私钥不进产品/仓库/CI**；
- license 本地 Ed25519 验签 + 机器码 + 到期/宽限 + 时钟检测（详见 licensing.md）；
- 续费：新订单新 license（同机器码、新到期），旧置 `replaced`；
- 退款：未签发 7 天可退；已签发按数字化商品政策不退（购买页显著提示+勾选）；退款后 license 标记 revoked（离线现实：不能远程关停，靠下次换机/续费时生效）。

### 3.1 license 与功能门禁（收费真正落地的地方）

- 状态：`free` → `trial`（14 天全功能）→ `paid`（年付/买断）→ `grace`（14 天）→ `expired`；
- feature 位：`mcp` / `batch` / `audit_export` / `custom_packs` / `tif` / `d3d` 等（见 licensing.md §3.3）；
- **门禁放在引擎内部**（HTTP `create_job` + `JobManager.create` + `mcp_server.py` 工具入口 + 前端提示），而不是 DSH 插件：保证 Claude Desktop / Cursor / DSH 三个客户端共享同一份本地授权，无法只改插件绕过；
- 免费额度：3 份/天、20 页/份、OCR 10 页/份、通用规则包、无 MCP/批量/审计导出（free-tier.md）；
- 试用：14 天全功能（含 MCP），到期回 free；时钟回拨不延长。

## 4 L2 / DSH「检测」怎么变成收费入口

按现有商业化口径，**MCP 属于专业版 feature**（licensing.md §3.3）；L2 的 DSH 检测面板天然是"付费墙前的体验面"：

| 场景 | 体验 | 收费动作 |
|---|---|---|
| 免费用户打开检测面板 | 能看到最近任务/自有文件检测状态，但 `sanitize_file` 等 MCP 工具返回 `feature_required` + 升级 CTA | 弹内购二维码（A/B） |
| 试用用户 | 14 天全功能（含 MCP/检测面板），顶部"试用剩 N 天" | 到期前 7/3/1 天提示续费 |
| 专业版 | 全功能，面板显示"专业版·到期日" | 续费/换机/开票入口 |
| 团队/机构 | 按席位/合同 | 对公/合同/人工签发 |

DSH 侧实现要点：

- **升级 CTA 只做展示与跳转**：DSH Client 插件显示授权状态/价格/二维码；支付密钥、订单密钥永不进插件；
- **Host 插件仅在用户点击时联网**（B 模式），调用官方商业服务建单/轮询；A 模式不联网，只渲染静态购买码；
- **绝不让模型自动购买**：MCP 工具返回 `license_required` + 购买 URL，由用户点击；工具描述明确"不得代用户支付/扫码"；
- DSH 插件可卸载/停用，但**授权在引擎侧**：卸载插件不影响授权文件，重装仍在；
- 内购入口同时出现在：Sanitized_Data 控制台「升级」、`/license` 授权页、DSH 检测面板；
- **老用户迁移**：licensing 首次上线时，建议给已安装用户赠送 1 年个人版/试用（monetization D4 建议），避免"原来免费现在收费"的口碑反噬；MCP 是否在 v1.x 保持免费、v2.0 起付费，需要拍板。

## 5 ICP 前过渡方案（现在就能开始收钱）

### 5.1 三套过渡通道

| 通道 | 适用 | 用户动作 | 收款方 | 授权交付 | 合规注意 |
|---|---|---|---|---|---|
| **对公转账 + 合同** | 团队/机构/企业早鸟 | 签合同/转账/提供机器码 | 企业对公账户 | 人工签发 license 文件/激活码 | 发票、合同、对账；推荐先用 |
| **合规平台卖授权码** | 个人早鸟 | 平台下单付款 → 收卡密/授权码 → 软件内输入 | 平台代收（有赞/微店等，需企业入驻） | 卡密兑换/人工签发 | 平台虚拟商品类目规则；抽佣；对账多一层 |
| **人工预售/内测** | 种子用户 | 微信/邮件登记 → 对公或平台 | 对公 | 人工签发 | 不面向公众大规模公开售卖 |

**明确不做**：个人微信/支付宝**个人收款码**收经营性款项（税务/合规风险）；二次清算类聚合支付（Ping++/虎皮椒等，合规风险高，仅极端过渡且需法务确认）。

### 5.2 ICP + 商户号下来后的切换清单

1. 域名备案完成 → 商业站点 HTTPS 上线（`buy.xxx.com`）；
2. 微信支付商户号 / 支付宝应用签约（经营类目选"软件/信息技术服务"）→ 沙箱 → 真实小额；
3. 电子发票（云开票）开通；
4. 用户协议/隐私政策/退款政策/EULA 上线（购买页显著提示+勾选）；
5. B 模式 Native 扫码上线；A 模式保留兜底；
6. 对账/退款/客服 runbook 演练（每日渠道账单 vs 订单）；
7. 早鸟价/限量活动按合规要求（不虚构原价/倒计时）。

### 5.3 关键路径（建议并行启动）

- **M0（本周）**：确认主体/对公/域名/ICP 进度/税控；提交商户号申请；协议交法务；
- **M1（1–2 周）**：W1 授权内核 + W2 免费版 + 内购入口 **A/B 双通道客户端预置（B 默认休眠）**（不依赖资质）；
- **M2（1–2 周）**：商业服务骨架 + 沙箱（订单/回调/签发/邮件/后台）；
- **M3（资质到位后 1–2 周）**：真实支付联调 + 发票 + **B 仅切服务端配置（客户端已内置，无需发版）**；
- **M4**：早鸟发售 + 对账/客服/发票跑通。

| 项 | 现状 | 代码/文档侧预留 | 何时提供 |

| 支付宝 | 待签约 | `ALIPAY_APP_ID` / 应用私钥 / 支付宝公钥 / 网关 | 签约后安全渠道 |

**接口预留原则**：

- 代码里只放 `.env.example` / 配置模板（键名+说明），**不填真实密钥**；密钥通过密码管理器/企业微信等安全渠道提供，绝不贴聊天/提交仓库；
- 支付密钥、APIv3 密钥、签名私钥只在商业服务/签名器主机；**产品安装包不含任何商户密钥/银行凭证**；
- 银行账户只用于结算与发票信息，API 不需要银行凭证；
- 商业服务接口按 [payment-invoice.md](payment-invoice.md) §7 先落地（订单/查询/绑定/回调/卡密/发票），联调时再填入商户参数；
- 联调阶段用沙箱 + 测试密钥对；生产密钥上线前做一次密钥轮换与权限核对。

## 8 风险与合规清单

| 风险 | 对策 |
|---|---|
| ICP/商户号延迟 | A 模式 + 对公/平台过渡先卖；不公开承诺"即时自动解锁" |
| 个人收款码/二次清算 | 明确禁止；财务/法务复核 |
| 回调伪造/金额不符/重复支付 | 验签+金额核对+幂等+退款队列+告警（payment-invoice.md §8） |
| 私钥泄露 | 签名器独立/权限/备份/轮换/审计；不进仓库/安装包 |
| 本地破解 | 接受残留风险；签名+机器绑定+门禁+低价+更新；不承诺绝对防破解 |
| 退款/消保 | 未签发 7 天可退；已签发按数字化商品政策，购买页显著提示+勾选（法务审） |
| 发票/税务 | 开票内容/税率财务确认；退款红冲 |
| 个人信息（PIPL） | 只收交付/开票必需信息；设备码哈希；不收集用户文件；隐私政策 |
| 老用户口碑 | 首次收费给老用户赠送/试用；MCP 付费时间点提前公告 |
| ICP 许可证问题 | 法务/属地通管局确认"自营软件销售"是否需要增值电信业务经营许可证 |
