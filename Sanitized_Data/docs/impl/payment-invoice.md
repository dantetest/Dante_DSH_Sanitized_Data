# 03 · 支付与发票设计（购买服务 / 订单 / 授权签发 / 开票）

> **状态**：设计规划（未改代码）· 2026-10-20 · 关联 [商业化总览](monetization.md)、[01 离线授权](licensing.md)、[04 价格页](pricing-page.md)
> **边界**：支付/发票服务是**独立商业系统**，不进入产品安装包、不影响本机引擎零外呼；本批只设计，不写代码。
> **费率/资质以微信支付、支付宝官方最新要求及签约合同为准**；本文金额为设计用，最终以 09 报告定价与市场侧确认价为准。

---

## 0 结论先行

1. **商业侧独立部署**：官网静态页 + 购买服务（订单/支付/授权签发/发票/后台）部署在公网服务器；产品只负责「导入 license」。
2. **支付主通道**：微信支付（Native 扫码 + 手机 H5）+ 支付宝（电脑/手机网站支付）**直连**；团队/机构支持**对公转账 + 合同 + 人工签发**；商户号未下来前用**过渡方案**（见 §16），不阻塞早鸟。
3. **主流程（先付款后绑定）**：选版本 → 填联系方式/发票需求 → 支付 → 回调确认 → 绑定机器码 → 签发并下载 `license.json` → 邮件送达 → 开票。
4. **发票**：电子普通发票自动/半自动（3 个工作日内），增值税专用发票人工审核（7 个工作日内）；退款走红冲/作废。
5. **防伪与对账**：回调验签、金额核对、幂等、绑定令牌一次性、后台 2FA、每日对账；授权私钥只在授权服务器。

## 1 系统组成与部署

```
公网服务器（建议 2C4G 起，独立于产品）：
  nginx（TLS，备案域名，如 cka.blctek.com / buy.blctek.com）
   ├─ /                 静态官网（首页 / 价格 / 下载 / FAQ / 协议）
   ├─ /buy              购买页（静态 + 表单）
   └─ /api, /callback   购买服务（FastAPI/Flask + SQLite/Postgres）
                          ├─ 支付：微信支付 APIv3 / 支付宝开放平台
                          ├─ 签发：调用独立 signer（Ed25519 私钥，独立进程/主机，
                          │        仅接受「DB 已 paid + 已绑定」的签发请求；sku/金额/到期
                          │        一律由 DB 派生，不接受 HTTP 传参）
                          ├─ 发票：开票队列（第三方云开票 API 或人工）
                          ├─ 邮件：SMTP（阿里云邮件推送/腾讯云 SES）
                          └─ 后台：订单/授权/绑定/退款/发票/报表（2FA）

本机产品（离线）：
  导入 license.json → 本地验签 → 解锁
```

**技术选型建议**：Python 3.12 + FastAPI + SQLite（WAL）+ Jinja/静态页；规模上来再换 Postgres。理由：与团队现有 Python 技能栈一致；不引入 Node/Java 运维；授权签发可直接复用 `cryptography`。

> **签名器（signer）独立**：逻辑上属于购买服务，但部署上必须是**独立 systemd/独立主机 + 内网 socket**，不暴露公网、不随购买服务进程一起被攻破；详见 §10。

**为什么不塞进产品仓库/安装包**：产品承诺禁网、无账号；商业站需要公网、支付回调、发票、用户手机号——两者混在一起会破坏安全边界、扩大攻击面、拖大安装包。

## 4 主流程

### 4.1 个人/专业版（主流程，先付款后绑定）

```
用户                         官网/购买页                 购买服务                     支付渠道
 │  选版本/填手机号邮箱/发票需求  │                            │                          │
 │────────────────────────────▶│  POST /api/order            │                          │
 │                              │───────────────────────────▶│ 建订单(pending)           │
 │                              │◀───────────────────────────│ 返回支付二维码/跳转URL     │
 │  扫码/支付                    │                            │                          │
 │───────────────────────────────────────────────────────────┼─────────────────────────▶│
 │                              │                            │◀── 支付回调(验签) ────────│
 │                              │                            │ 订单→paid（幂等）         │
 │                              │◀───────────────────────────│ 返回 bind_token（一次性）  │
 │  回应用内复制机器码            │                            │                          │
 │────────────────────────────▶│  POST /api/order/{no}/bind │                          │
 │                              │───────────────────────────▶│ 校验 token/订单/机器码     │
 │                              │                            │ 生成 license(payload+sig) │
 │                              │◀───────────────────────────│ 返回 license + 下载链接    │
 │  下载 license.json            │                            │                          │
 │  导入本机 → 解锁               │                            │                          │
 │                              │                            │ 邮件发 license/发票信息    │
 │                              │                            │ 开票队列（普票自动/专票人工）│
```

- **为什么先付款后绑定**：降低购买页流失（下单时不必先找机器码）；绑定页可在支付后引导用户回应用内复制。
- **绑定令牌**：`bind_token` ≥128 bit、15 分钟有效、一次性、服务端只存哈希；过期可重新获取；邮件里的「重新下载链接」token 7 天有效。
- **超时/关闭**：订单 2 小时未支付自动关闭；已支付未绑定订单长期有效（建议 90 天内可绑定，超时客服处理）。
- **发票需求**：下单时收集（不需要/普票/专票 + 抬头/税号等），也可支付后在「订单详情」补填。
- **授权交付**：绑定页直接下载 + 邮件附件（license.json 体积 <10KB）；邮件同时给「重新下载链接」（带 token）。
- **邮件失败**：页面始终展示下载入口；后台可重发。

### 4.2 续费

- 应用内授权页/到期横幅 → 打开官网续费链接（`?renew=<license_id>`，**URL 不带机器码**；服务端按已绑定 license 反查机器码并校验）；
- 购买服务识别续费：订单带 `renew_of`；签发新 license（同机器码、新到期日）；
- 用户导入新文件覆盖旧文件（产品自动备份 `.bak`）；
- 续费优惠（如老用户 9 折）用 coupon 实现。

### 4.3 团队版

1. 管理员购买 `team_*` → 支付成功后在「团队授权」页录入 N 个成员的机器码（可分批），或生成邀请链接让成员提交机器码；
2. 服务端签发 1 个含 N 个机器码的 `license.json`；
3. 管理员分发给成员；成员各自导入；
4. 后续加席/换人：后台「重签」（生成新文件，旧文件仍可被旧机器用——离线现实，合同/管理约束）；
5. 管理员可下载成员绑定明细（P1）。

### 4.4 机构版

1. 官网/客服提交线索（单位、人数、场景、部署方式）；
2. 销售报价（3.88 万起，按席位/部署范围/定制规则）；
3. 合同 + 对公转账/开票；
4. 后台登记合同与服务器机器码 → 签发 `org` license；
5. 交付工程师现场/远程部署 + 验收单；
6. 续费提醒由运营跟进（年度）。

### 4.5 按次包

- 购买 `doc_10` 后发放「按次兑换码」（10 次，30 天有效；服务端记录）；
- 产品内「按次授权」导入兑换码 → 本地计数（与免费限额类似，需防篡改，见 [02 §3](free-tier.md)）；
- **按次不主动推**（09 报告 §5.5）：仅官网可选，页面不突出；企业/团队不开放按次。

> 按次授权在离线产品里需要额外一套「次数 license」；P0 可先不做，等验证「按次需求真实存在」再上（决策见 §17 Q6）。

## 5 支付渠道对比与建议

| 渠道 | 适用 | 资质/接入 | 费率（以合同为准） | 开发量 | 回款 | 发票 | 风险/备注 |
|---|---|---|---|---|---|---|---|
| **微信支付（Native/H5/JSAPI）** | PC 扫码、手机 H5、公众号 | 企业商户号、备案域名 | 常见 0.6% | 中 | T+1 | 可与开票系统对接 | 主力通道；需 APIv3 证书 |
| **支付宝（电脑/手机网站支付）** | PC、手机浏览器 | 企业账号、应用签约 | 常见 0.6% | 中 | T+1 | 同上 | 主力通道；RSA2 |
| **对公转账** | 团队/机构/合同客户 | 对公账户、合同 | 0 | 低 | 人工确认 | 专票 | 必须支持；人工签发 |
| 第三方聚合（Ping++/虎皮椒/PayJS 等） | 商户号未批时过渡 | 企业资质 | 1–3%（含服务费） | 低 | T+1/T+7 | 较麻烦 | **二次清算合规风险**，仅过渡 |
| 知识付费/微店/有赞 | 早鸟过渡、发卡密 | 平台入驻 | 1–5% | 极低 | 平台结算 | 平台代开/自开 | 品牌弱、价格体系难控，仅过渡 |
| 淘宝/闲鱼店 | 引流/低价测试 | 个人/企业店 | 平台佣金 | 极低 | 平台结算 | 困难 | **不建议**：价格体系与专业品牌受损 |

**建议**：
- P0：微信 + 支付宝直连（若已有商户号则 1–2 天可接沙箱）；对公转账人工流程同步上线；
- 商户号审批中：先用「对公转账 + 人工签发」卖早鸟（企业客户）或「微店/有赞发卡密」（个人客户），并在页面注明「支付渠道升级中」；
- 不做「个人收款码」收企业客户款（税务/合规风险）。

## 6 数据模型（SQLite/Postgres 通用）

```sql
-- 订单
orders(
  id INTEGER PK, order_no TEXT UNIQUE, sku_id TEXT, sku_snapshot JSON,
  amount_cents INTEGER, currency TEXT DEFAULT 'CNY',
  status TEXT,             -- pending|paid|closed|refunded|refund_pending
  campaign_id TEXT, coupon_code TEXT,
  buyer_phone TEXT, buyer_email TEXT,
  invoice_need TEXT,       -- none|personal|company_special
  source TEXT,             -- utm/来源
  renew_of TEXT,           -- 续费订单关联 license_id
  upgrade_from TEXT,       -- 升级订单关联旧 license_id
  reissue_fee_cents INTEGER DEFAULT 0,   -- 换机/服务费
  seat_delta INTEGER DEFAULT 0,          -- 团队加席
  order_access_token_hash TEXT,          -- 订单查询 token（32B 随机，哈希存储）
  paid_at TEXT, bind_token_hash TEXT, bind_expires_at TEXT,
  created_at TEXT, updated_at TEXT
);
-- 授权
licenses(
  id INTEGER PK, license_id TEXT UNIQUE, order_id INTEGER,
  sku TEXT, seats INTEGER, max_devices INTEGER,
  machine_codes JSON, term TEXT, features JSON,
  issued_at TEXT, not_before TEXT, expires_at TEXT, updates_until TEXT,
  key_id TEXT, sig TEXT, status TEXT,   -- active|replaced|revoked
  downloads INTEGER DEFAULT 0
);
-- 发票
invoices(
  id INTEGER PK, order_id INTEGER, type TEXT, title TEXT, tax_no TEXT,
  address_phone TEXT, bank_account TEXT, amount_cents INTEGER,
  status TEXT,             -- pending|issued|red|void
  invoice_no TEXT, file_path TEXT, issued_at TEXT, operator TEXT
);
-- 退款
refunds(
  id INTEGER PK, order_id INTEGER, amount_cents INTEGER, reason TEXT,
  status TEXT, channel_refund_id TEXT, processed_at TEXT, operator TEXT
);
-- 支付流水：一单可多次尝试/多通道；金额一律 int 分
payments(
  id INTEGER PK, order_id INTEGER, channel TEXT,
  out_trade_no TEXT UNIQUE,        -- order_no + "-" + channel + "-" + seq
  transaction_id TEXT,             -- 渠道交易号
  amount_cents INTEGER, currency TEXT DEFAULT 'CNY',
  status TEXT,                     -- created|paid|failed|refunded
  raw_ref TEXT, paid_at TEXT, created_at TEXT,
  UNIQUE(channel, transaction_id)
);
-- 卡密/兑换码：仅商户号未批时的过渡方案使用（见 §16）
redeem_codes(
  id INTEGER PK, code_hash TEXT UNIQUE, sku_id TEXT, term TEXT, credits INTEGER,
  order_id INTEGER, used_at TEXT, used_by_machine TEXT, created_at TEXT
);
-- 后台账号/审计/通知/优惠码
admin_users(id, username, password_hash, totp_secret, role, created_at);
audit_logs(id, actor, action, target, detail_json, created_at);
notifications(id, order_id, channel, template, status, sent_at, error);
coupons(code, type, value, sku_scope, max_uses, used, valid_from, valid_to);
```

> `order_no` 必须是**随机 20 字符**（不可预测/不可枚举），不要用 `ord_YYYYMMDD_0001` 这类流水号；`orders.amount_cents` 是**应付**（expected）；实际到账以 `payments.amount_cents` 为准，二者必须逐笔比对。订单/升级/换机/加席等金额变化通过 `upgrade_from / reissue_fee_cents / seat_delta` 字段与「新订单」表达（P0 先人工后台登记）。

**原则**：订单/发票数据按会计档案要求保存（具体年限由财务确认，通常 ≥10 年）；用户手机号/邮箱仅用于交付与服务；**绝不**收集/上传用户要脱敏的文件。

## 7 接口契约（建议）

### 7.1 公开接口

| 方法/路径 | 请求 | 响应 | 说明 |
|---|---|---|---|
| `GET /api/catalog` | — | `{skus:[...], campaigns:[...]}` | 价格页可用（静态页也可构建时内联） |
| `POST /api/order` | `{sku_id, phone?, email?, invoice_need?, coupon?}` | `{order_no, amount, pay:{channel, qr/url}}` | 建单 + 拉起支付 |
| `GET /api/order/{order_no}` | `?token=`（**订单访问 token**，32B 随机，7 天有效；邮件/页面带） | `{status, sku, amount, bind_token?}` | 轮询/回跳；错误 token 统一 404，防枚举 |
| `POST /api/order/{order_no}/bind` | `{bind_token, machine_code}` | `{license, download_url, expires_at}` | 绑定机器码并签发；自助绑定只成功一次 |
| `POST /api/redeem`（**仅过渡方案启用**） | `{code, machine_code}` | `{license, download_url}` | 卡密兑换（见 §16）；一次性核销 |
| `GET /api/license/{license_id}.json` | `?token=`（`download_token`，服务端哈希校验） | license 文件流 | 下载/重下 |
| `GET /api/download/{file}?token=`（P1） | `download_token` + `updates_until` 校验 | 安装包流 | 买断更新期过后不再提供新版本下载（产品内仅软提醒） |
| `POST /api/invoice` | `{order_no, type, title, tax_no, ...}` | `{invoice_id, status}` | 补开发票（需订单访问 token） |
| `POST /callback/wechat` | 微信回调 | `{code:"SUCCESS"}` | 验签 + 幂等 |
| `POST /callback/alipay` | 支付宝回调（form） | `success` | RSA2 验签 + 幂等 |

### 7.2 后台接口（登录 + 2FA）

- 订单：列表/搜索/详情/手工标记已付（对公）/关闭/退款；
- 授权：查看/重签/重发/绑定明细/撤销（仅标记，不远程关停）；
- 发票：开票/重开/红冲/导出；
- 团队：席位与机器码管理、批量导入；
- 报表：日/月收入、渠道、退款、发票、早鸟消耗；
- 审计日志（谁在何时做了什么）。

### 7.3 错误码

`order_not_found`、`order_closed`、`order_not_paid`、`bind_token_invalid`、`bind_token_expired`、`machine_code_invalid`、`sku_inactive`、`campaign_exhausted`、`coupon_invalid`、`amount_mismatch`、`duplicate_callback`（幂等返回成功）、`rate_limited`。

## 8 回调安全与幂等（关键）

| 通道 | 验签 | 校验 | 幂等 |
|---|---|---|---|
| 微信支付 APIv3 | `Wechatpay-Signature` + 平台证书/公钥；`Wechatpay-Serial` | 解密 resource；核对 `out_trade_no`、`amount.total`、`mchid`、`appid`、`trade_state=SUCCESS` | 以 `transaction_id` 唯一键；重复回调直接返回成功 |
| 支付宝 | RSA2 验签（支付宝公钥）；`app_id`/`seller_id` 校验 | `trade_status=TRADE_SUCCESS/TRADE_FINISHED`、`out_trade_no`、`total_amount` | 以 `trade_no` 唯一键；重复返回 `success` |
| 对公转账 | — | 银行流水号 + 人工核对 | 后台人工标记，需二次确认 + 审计 |

- 回调必须 **HTTPS**；服务器时间同步；回调处理失败要落库 + 告警，允许重放；
- **金额口径（关键）**：订单应付 `expected_cents` 由 SKU 快照计算（**int 分，禁用浮点**）；微信 `amount.total` 本身是分（int），直接比；支付宝 `total_amount` 是元字符串（如 `"199.00"`），必须 `Decimal(...) * 100` 转 int 分后比；币种必须 CNY；金额不符 → 不发货 + 告警；
- **多通道重复支付**：`out_trade_no = order_no + "-" + channel + "-" + seq`；`payments` 以 `(channel, transaction_id)` 唯一；同一订单若出现第二笔成功支付 → 自动进入退款队列 + 告警，不得重复签发；
- 回调先落「事件表」再异步处理（防超时丢单）；
- **微信**：除验签外校验 `timestamp` 在 5 分钟内（防重放）、平台证书轮换时新旧 `Wechatpay-Serial` 并存、回源 IP 校验（可选）；**支付宝**：`notify_id` 去重、校验 `app_id`/`seller_id`、区分 `TRADE_SUCCESS`（可退）与 `TRADE_FINISHED`（不可退）；
- **绑定语义**：自助 `/bind` 同一订单**只允许成功一次**（重复请求幂等返回同一 license）；**换绑/换机只允许后台/客服操作**，生成新 license、旧置 `replaced`；不允许用户自助换绑；
- **令牌安全**：`bind_token` ≥128 bit、15 分钟有效、一次性、服务端只存哈希；订单访问 token 32B、7 天有效；`download_token` 只用于 license 下载；错误/过期 token 统一 404；找回必须「短信验证码或邮件 magic link」；**不能只凭手机号枚举订单**；
- **防刷**：下单/绑定/查询接口按 IP + 手机号限流；绑定失败次数达阈值转人工客服。

## 9 发票设计

### 9.1 类型与流程

| 类型 | 适用 | 收集信息 | 开具方式 | 时限 |
|---|---|---|---|---|
| 电子普通发票（个人） | 个人购买 | 抬头（个人/单位）、税号（单位抬头时） | 第三方云开票 API 自动，或财务手工开具 PDF | 3 个工作日 |
| 电子普通发票（单位） | 团队/小企业 | 单位名称、税号 | 同上 | 3 个工作日 |
| 增值税专用发票 | **任何购买方，只要具备一般纳税人资质**（不按 SKU 限制，个人版也可开） | 名称、税号、地址电话、开户行账号 | 人工审核 + 税控/云开票 | 7 个工作日 |

> **不按 SKU 限制发票类型**：个人版用户所在单位报销也可能需要专票；是否可开专票取决于购买方纳税人资质与提供的信息，而不是买了哪一档。价格页只写「专票需提供资质信息」，不要写「个人版仅普票」。

### 9.2 流程

```
支付成功 → 发票需求入库(pending)
   ├─ 普票：调用开票服务/人工 → 生成 PDF → 邮件 + 订单页下载 → status=issued
   └─ 专票：财务审核资料 → 开具 → 邮件/邮寄 → status=issued
退款 → 原发票红冲/作废 → status=red → 重新开票（如需）
```

### 9.3 开票内容与税率（需财务/税务确认）

- 建议项目：**信息技术服务*软件服务费**（或按主管税务机关核定的「软件产品」类目）；
- 金额 = 订单实付金额（含税价，含优惠后实付）；早鸟价按实付开票；
- **不在本设计里替财务定税目/税率**；实施前由财务确认并固化到开票模板；
- 发票抬头与付款方不一致时需说明（对公转账尤其常见）。

### 9.4 开票服务商选择

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 自建税控/电子发票平台 | 数据可控 | 对接复杂、税控设备/资质 | 有现成税控能力才用 |
| 第三方云开票 API（诺诺/高灯/百望等） | 接入快、支持 PDF/红冲 | 按张收费、需企业资质 | **P0 推荐**（普票自动化） |
| 人工 Excel + 税控机 | 零开发 | 量大易错、时效差 | 仅过渡/专票 |

### 9.5 发票数据与隐私

- 发票信息只用于开票与存档；后台仅财务/管理员可见；
- 不做营销用途；隐私政策写明；
- 发票 PDF 存储加密/权限控制，定期备份。

## 10 授权签发集成

- **签名器**：独立进程/模块（`commercial/signer/`）或独立内网主机，读取私钥文件（权限 0400/600，仅服务账号可读，账号无 shell），输入 payload → 输出 `{schema, alg, key_id, payload, sig}`；
- **签发边界（关键）**：signer **只接受**「DB 里 `orders.status=paid` 且已绑定机器码」的签发请求；`sku`、金额、到期日、features 一律由 signer 查 DB 派生，**不接受 HTTP 传参**；团队/机构签发加人工审批；
- **调用方**：购买服务在「支付成功 + 绑定机器码」后调用签名器；签名器写 `licenses` 表 + `audit_logs`（谁/何时/订单/机器码/有效期）；
- **幂等**：同一订单 + 同一机器码 → 返回已签发 license（不重复签）；换绑 → 新 license，旧置 `replaced`；
- **密钥**：生产私钥只在一台授权服务器；离线备份加密存放；`key_id` 支持轮换（见 [01 §8.4](licensing.md)）；
- **签发测试**：独立测试密钥对，签名器支持 `--key test` 仅供测试环境；
- **异常**：签名器不可用 → 订单保持 paid、页面提示「授权生成中，1 小时内邮件发送」；恢复后重试队列。

## 11 退款、售后与条款

### 11.1 退款规则（建议，法务确认）

| 场景 | 规则 |
|---|---|
| **未完成绑定签发（未生成 license）** | 7 天内可无理由退款（原路退回）；以 `licenses` 表是否存在为唯一判据（下载次数不作为判据，因为「保存响应」不可检测） |
| 已生成/已激活授权 | **不支持无理由退款**（数字化商品，购买页显著提示并勾选确认） |
| 重复支付/支付异常 | 核实后全额退（含多通道重复支付） |
| 功能严重缺陷无法使用 | 客服核实后可退/换 |
| 团队/机构 | 按合同约定 |

> 法律依据：《消费者权益保护法》第 25 条对「在线下载或消费者拆封的音像制品、计算机软件等数字化商品」的不适用无理由退货规定；购买页必须**显著提示**并让用户主动勾选「已阅读退款政策」，否则条款可能无效（法务审）。

### 11.2 退款流程

```
用户申请（客服/后台）→ 核对订单/授权状态 → 审批
  → 原路退款（微信/支付宝 1–7 个工作日；对公 3–10 个工作日）
  → license.status=revoked（仅记录，不远程关停）
  → 发票红冲/作废
  → audit_log + 邮件通知
```

### 11.3 售后

- 授权找回/换机/导入失败：客服流程（见 [01 §8.2/8.3](licensing.md)）；
- 发票重开/换开：7 天内；
- 客服 SLA 建议：工作日 24 小时内响应；企业微信/邮箱双通道。

## 13 部署与运维

| 项 | 建议 |
|---|---|
| 服务器 | 2C4G 起，独立于产品演示机；Ubuntu/Debian；Docker 可选 |
| 反向代理 | nginx：TLS、`client_max_body_size 20m`、限流（订单/回调不同 zone） |
| 进程 | systemd：`buy-web`、`buy-worker`（发票/邮件/重试队列） |
| 数据库 | SQLite WAL（单机够用）→ 订单量上来换 Postgres；每日备份 |
| 队列 | 先用 DB 表 + 定时 worker（简单可靠）；量大再上 Redis/Celery |
| 邮件 | SMTP 服务商（阿里云/腾讯云）；SPF/DKIM/DMARC；退信处理 |
| 对账 | 每日拉取微信/支付宝账单 → 与 `orders.paid` 对账；差异告警 |
| 结算 | T+1 到对公账户；财务按订单/发票做账 |
| 值班 | 支付失败/回调异常告警到企业微信；早鸟期每天看数 |

### 13.1 运营 Runbook（摘要）

1. **每日**：对账（渠道账单 vs 订单）；异常订单处理；发票队列清空；退款审批；
2. **每周**：授权重签/换机申请；客服问题归类；早鸟消耗与转化；
3. **每月**：收入/退款/发票报表；渠道费率核对；密钥/证书有效期检查（微信证书、TLS）；
4. **事件**：支付回调失败 → 查日志/重放；签名器故障 → 暂停绑定、页面提示、恢复队列；私钥疑似泄露 → 轮换 key_id + 通知。

## 16 过渡方案（商户号/开票未就绪时）

| 方案 | 适用 | 做法 | 风险 |
|---|---|---|---|
| **对公转账 + 人工签发** | 团队/机构/早鸟企业客户 | 页面展示对公账户；用户转账后提交凭证；后台核对 → 人工签发 license + 收据/后补发票 | 慢，但合规、零开发 |
| 微店/有赞/知识付费 | 个人早鸟 | 平台上架「早鸟授权」商品，自动发兑换码/卡密；用户拿卡密到官网「兑换」页换 license | 平台抽佣、品牌弱、对账多一层 |
| 第三方聚合支付 | 个人 | 接入 Ping++/虎皮椒等（需企业资质） | 二次清算合规风险、费率略高 |
| 淘宝/闲鱼 | 不建议 | — | 价格体系/品牌受损 |

**卡密兑换的完整设计（若采用）**：`redeem_codes` 表（`code_hash` 唯一、`sku_id`、`term`、`credits`、`order_id`、`used_at`、`used_by_machine`）；接口 `POST /api/redeem {code, machine_code}` → 校验一次性 → 按 SKU 签发 license（或按次 credits 签发）→ 记录订单/对账口径；后台可批量生成/导出卡密。**新增 2–3 人日**（含防刷、限流、对账）。

**若 D1 未定且不做卡密**：早鸟期只开放「对公转账 + 人工签发」（企业客户），个人客户等支付资质到位再开卖；**删除**「微店/有赞发卡密」路径，避免「页面写了但兑不了」。

**原则**：过渡期也**不要**用个人微信/支付宝收款码收企业客户的钱；收据/发票必须能对上订单与授权。
