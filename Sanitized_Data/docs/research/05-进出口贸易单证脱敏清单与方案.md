## 0 结论摘要

### 0.1 十条结论

1. **单证数量与链条**：进出口贸易全流程涉及 **43 类**单证/文件（§1，其中高频核心 16 类）；同一批出口业务通常至少包含"合同 → 发票 → 装箱单 → 提单/运单 → 报关单"五件套，信用证业务再加"信用证 + 保险单 + 汇票/交单面函"。
2. **敏感条目**：共梳理 **48 项**敏感条目（L3 级 9 项 / L2 级 30 项 / L1 级 9 项，§2）。真正的高风险不是传统个人信息，而是**单证号码 + 金额价格 + 银行账户 + 签字盖章 + 最终用户/管制信息**这五类。
3. **现有规则覆盖不均**：`common` 包的手机号/邮箱/身份证/银行卡/USCC/中文机构名/人名/地址、`finance-cn` 的银行账号/IBAN 可直接复用；但**贸易特有号码（集装箱号、提单号、报关单号、发票号、合同号、许可证号）当前 0 覆盖**，**外币金额（USD/EUR）0 覆盖**，**英文公司名 0 覆盖**（§4，探针实验证实）。
4. **USCC 校验器已实现但规则未启用**：`uscc_checksum` 在 `detectors/regex_det.py:140-155` 已实现，但 `rules/common.yaml:100-109` 的 `cn.uscc` 未声明 `validate`，导致**校验位非法的 18 位串也会命中**（附录 C 实验值 `91330200MA2AB1C2D3` 校验位应为 J，实测仍被识别）。
5. **大量贸易场景必须换名且"保形合法"**：集装箱号（ISO 6346 第 11 位校验）、空运单号（IATA 11 位、末位 mod 7）、统一社会信用代码（GB 32100 mod 31）、身份证（GB 11643 mod 11-2）、IBAN（ISO 13616 mod 97）、报关单号（18 位结构）——换名后必须重算校验位或保持结构，否则文件一交给银行/海关就"一眼假"（§3、§5）。
6. **trade-cn 规则包可零代码先落地**：现有规则引擎支持 YAML 热加载（`rules.py:313-399`），新增 `trade-cn.yaml`（含 `include: [common]`）**不需要改代码**；但校验位、英文机构名、字段级取值、跨单证一致性必须写代码（§5，P0 配置 2–3 人日）。
7. **跨单证一致性是当前产品最大缺口**：`pipeline.Session` 是**每个任务（=每个文件）一个**（`jobs.py:88`），映射库也按 `job_id` 存储（`vault.py:52-66`），API 一次只收一个文件（`api.py:113-147`）——同一公司名在合同和发票里会被换成**两个不同假名**。必须引入"任务组 + 共享会话映射 + 勾稽检查"（§6，P2 10–15 人日）。
8. **两种出口必须彻底分开**：给 AI 做审核/翻译/填单 → 可逆换名版（映射加密、整批共享、金额同比例）；给银行/海关/客户 → **原件或不可逆涂黑件**，且不得用于申报（§6.4）。信用证（UCP600 表面相符）与带数字签名的电子单证**默认不做换名**，否则直接造成不符点或签名失效。
9. **风险边界必须写进产品文案**：产品只做"去标识化"，不做合规承诺；换名后的报关单**不能用于申报**（申报不实风险）；最终用户/最终用途/管制物项信息默认涂黑、不进入 AI 上下文；数据出境需按《促进和规范数据跨境流动规定》判断（§8）。
10. **总工作量约 20–30 人日（核心），含可选约 36 人日**：P0（trade-cn 规则包 + 样例 + 验收清单）2–3；P1 核心（校验器/替换工厂/英文机构名/字段检测/Verify 增强）8–12（PDF 表单域检测、映射导入导出为可选 +3.5）；P2 核心（任务组 + 共享映射 + 勾稽引擎 + 前端）10–15（PDF 表格结构可顺延 +3）（§6.5、§7.4）。

**关于两类"过时/易混淆"单证的说明（对用户原始清单的校正，供审核）：**

- **核销单**：国家外汇管理局、海关总署、国家税务总局自 **2012-08-01** 起取消出口收汇核销单，出口报关不再提供核销单，退税也不再提供（见附录 A[^1]）。**存量历史文件仍可能出现**，规则包保留识别能力即可，不建议投入专门解析器。
- **报检单**：2018 年关检融合后，报关单与报检单整合申报（"两单合一"），新业务不再单独出现原报检单（附录 A[^2]）；历史档案中仍有。真正需要关注的是整合后的**报关单**中"检验检疫"相关栏位。

### 1.4 单证间的主从关系（决定"跨单证一致性"的对象）

- **主单证**：合同（法律基础）→ 商业发票（金额/品名基准）→ 报关单（申报口径）。
- **从单证**：装箱单、提单/运单、保险单、原产地证、检验证书、许可证均须与主单证在**品名、数量、金额、日期、主体**上互相印证。
- **银行单据链**：信用证条款是一张"清单"，商业发票、提单、保险单、装箱单、产地证、检验证都是它的"证据"；任一单据被换名/改数，都可能触发不符点（§3.4）。
- 因此**同一批业务的脱敏必须是"批级映射"**，而不是"每个文件独立换名"（§6）。

### 2.1 敏感级别与替换策略定义

级别沿用引擎现有 `L0–L3`（`config.py:42`，L3 最严）与"双轨出口"设计（`DESIGN.md:214-237`）。本方案在贸易场景中的口径：

| 级别 | 含义（贸易场景） | 默认策略（AI 可逆版） | 默认策略（人看不可逆版） | 例 |
|---|---|---|---|---|
| **L3** | 直接标识主体/资金/授权，泄露即造成实质损害；或涉出口管制 | 涂黑（black）优先；确需 AI 审查时用**可逆换名+内部映射**且不进入上下文的只读副本 | 涂黑/删除，不生成映射 | 银行账号、身份证、许可证号、签章、最终用户、佣金关系 |

策略枚举与代码一一对应（`rules.py:51`、`pipeline.py:208-223`）：`surrogate`（保形假值，可逆）、`mask`（部分遮蔽）、`black`（涂黑/删除，不可逆）、`drop`（删除）、`keep`（保留但仍进入"已识别清单"，便于审核与统计）。

> **关键约束**：对同一实体，"给 AI 版"与"给人看版"是**两条导出路径**（`jobs.py:473-482`：human 模式强制全部 `black`），不能共用同一成品。

### 3.2 关键校验算法要点（文档级）

**(1) ISO 6346 集装箱号校验（第 11 位）**

1. 取前 10 位：3 位箱主代码 + 1 位设备类别（U/J/Z）+ 6 位序列。
2. 字母转数值：从 A=10 开始递增，**跳过 11、22、33**（即 A=10、B=12、C=13 … K=21、L=23 …），数字保持原值。
3. 第 i 位（i 从 0 开始）乘以 2^i（1、2、4、8、16、32、64、128、256、512），求和。
4. 总和 mod 11，余数即校验位；余数为 10 时校验位记 0。
5. 示例（实测验证）：`CSQU3054383` → 加权和 6185 → 6185 mod 11 = **3** → 校验位 3，与末位一致，号码合法。

> 换名规则：保留 `CSQ`（箱主代码）与 `U`，替换 `305438` 为新的 6 位序列，按上式重算末位。**不要替换箱主代码**——BIC 注册的箱主代码指向真实船公司，编造可能与真实箱号撞车。

**(2) IATA 空运单号校验（第 11 位）**

1. 11 位数字：前 3 位航空公司数字代码（如 999=中国国际货运航空）+ 7 位序列 + 第 11 位校验。
2. 校验算法：前 10 位组成的整数 **mod 7**，余数即第 11 位（unweighted modulus 7，IATA 标准，附录 A[^6]）。
3. 示例（实测验证）：`999-1234567` → 9991234567 mod 7 = **6** → 完整号码 `99912345676`。

> 换名规则：保留航司代码，换 7 位序列，重算 mod 7。**注意**：不同航司代码的运单可能真实存在，换名后的号码应标注为"脱敏虚构号"，禁止用于实际查询/提货。

**(3) 统一社会信用代码校验（GB 32100）**

- 字符集 31 个：`0123456789ABCDEFGHJKLMNPQRTUWXY`（不含 I、O、S、V、Z）。
- 权重 17 位：`1,3,9,27,19,26,16,17,20,29,25,13,8,24,10,30,28`。
- 计算：Σ(字符值×权重) mod 31，校验值 = `(31 − 余数) mod 31` 对应字符。
- 现实现：`regex_det.py:140-155`（检测侧）与 `surrogate.py:367-369,725-743`（替换侧重算）；**检测侧未启用**。

**(4) 身份证校验（GB 11643，ISO 7064 MOD 11-2）**

- 权重 `7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2`；校验码表 `10X98765432`。
- 现实现：`regex_det.py:59-83`（检测）、`surrogate.py:362-365`（替换）。

**(5) IBAN 校验（ISO 13616）**

- 前 4 位移到末尾；字母 A–Z 转 10–35；对整个数字串 mod 97，余数必须为 1。
- 现实现：`regex_det.py:112-133`、`surrogate.py:353-359,862-875`。

**(6) 报关单号结构校验（18 位）**

- 正则骨架：`^\d{4}(19|20)\d{2}[01IE]\d{9}$`。
- 结构含义见 §3.1；**无校验位**，只能做结构+日期合理性校验（年份不超过当前年、关区代码在关区代码表内）。
- 换名规则：保留前 9 位，后 9 位顺序号换新；同时在映射库记录"虚构"标记。

**(7) HS 编码结构校验**

- 6 位国际 HS（第 1–2 位章、3–4 位目、5–6 位子目）；中国 10 位 = 8 位税则号列 + 2 位监管附加。
- 无校验位；只能做"前 2 位在 01–97、总长度为 6/8/10"的结构判断。
- **换名禁止**：HS 一变，归类、税率、监管证件、退税率全部改变，属于"改单"而非"脱敏"。

**(8) 金额大写联动**

- 英文：`SAY TOTAL USD ONE HUNDRED TWENTY-EIGHT THOUSAND ONLY`；中文：`人民币壹拾贰万捌仟元整`。
- 换名要求：**数字金额变化后，大写必须同步重算**；且必须保持"单价×数量=总价"与"总价=各分项合计"。
- 现实现：`surrogate.py:648-695` 的 `_fake_amount` 只做 ±25% 数字浮动，**不处理大写、不处理勾稽**（§4.1）。

### 3.4 信用证（L/C）的"严格单据条款"与脱敏冲突

- UCP600（ICC Publication No. 600）要求银行**仅凭单据表面**审单，单据数据不得与信用证条款/其它单据矛盾（UCP600 第 14–16 条；审单标准另见 ISBP 745），不符点即可拒付（附录 A[^7]）。
- 因此对 L/C 项下单据（发票、提单、保险单、装箱单、产地证、检验证、汇票）：
  1. **默认不做换名/改数**；给银行/开证行的版本必须是原件或仅去除与 LC 无关的附加标注。
  2. 若确需给 AI 做预审，必须整批共享映射、且金额/数量/日期/港口**不缩放**（否则 AI 会误判"不符点"）。
  3. 修改信用证号/开证行/受益人名称会直接导致单据不符；**建议涂黑而不是换名**。
- 结论：**L/C 单据是本项目中风险最高、最不建议脱敏的文档类型**；产品应在识别到"信用证/交单"关键词时给出强提醒，甚至默认禁用"换名出口"，只允许"涂黑副本（标注仅内部使用）"。

## 6 跨单证一致性与两种出口策略

### 6.1 为什么必须做"任务组"：现状证据

1. **会话是每文件一个**：`jobs.py:88` `session: pipeline.Session = field(default_factory=pipeline.Session)`；`pipeline.Session`（`pipeline.py:160-177`）只在单任务内保证"同值同映射"。
2. **映射库按任务存**：`vault.save_mapping(job.id, ...)`（`jobs.py:454-456`、`vault.py:52-66`），`load_mapping(job_id)`（`vault.py:69-78`）没有"组"的概念；`list_vault()`（`:111-115`）只列文件。
3. **API 单文件**：`/api/upload`（`api.py:113-124`）与 `/api/jobs`（`:128-147`）一次一个文件；没有批量/组接口。
4. **假值生成依赖会话状态**：`surrogate._rng_for` 的 seed 包含 `len(session.map)`（`pipeline.py:197`、`surrogate.py:346-350`），**同一原值在不同文件的实体顺序不同，可能得到不同假值**。
5. **金额独立抖动**：`_fake_amount` 对每个金额独立 ±25%（`surrogate.py:654-695`），即使同一文件内，单价与总价也会各抖各的，破坏"单价×数量=总价"（§3.3 J1）。

**结论**：当前产品适合"单文件、给人看、不可逆"的简单脱敏；**不适合"一批单证给 AI 做审核/翻译/填单"**——后者恰恰是贸易场景的核心需求。

### 6.2 方案对比

| 方案 | 做法 | 优点 | 缺点 | 工作量 | 建议 |
|---|---|---|---|---|---|
| **A. 任务组 + 共享会话（推荐）** | 新增 Group 模型：一次创建组，批量加入文件，所有文件共用同一个 `Session`/映射库；逐文件导出，组级 Verify + 勾稽检查；映射存 `group_id` | 真正解决跨文件一致；金额可做批级比例；可做勾稽 | 改动 `jobs.py`/`api.py`/`vault.py`/前端；需处理顺序稳定性 | 10–15 人日 | **P2 目标方案** |
| **B. 单文件 + 映射导入导出（过渡）** | 每文件独立处理，但支持把 `vault` 映射导出为 JSON，下一个文件"导入映射"再处理；用户手工保证顺序 | 改动小；无需前端大改 | 用户操作繁琐、易漏；无法自动勾稽；仍要重算假值 | 2–3 人日 | **P1 过渡** |

### 6.3 推荐方案 A 设计要点

**数据模型（文档级）**

```text
Group {
  group_id, name, created_at, pack_ids, strictness,
  files: [ { job_id, role(合同/发票/箱单/提单/报关单/LC/保单/产地证/EUC/其他) } ],
  session: Session（共享实体图）,
  status: drafting | detecting | reviewing | exported | verify_failed
}
```

**流程**

1. 创建任务组（选规则包含 `trade-cn`、strictness、业务类型模板）。
2. 批量上传文件 → 逐文件解析 + **用组共享 Session 检测/决策**（`pipeline.decide` 已支持传入 Session，`pipeline.py:180-205`；只需 `jobs.Job` 允许注入共享 Session）。
3. 组内审核（每文件页面对照；漏检补框仍落到共享 Session）。
4. 导出前执行**勾稽检查**（J1–J15）与**一致性检查**（同原值→同假值；同号码在 5 份文件中映射一致）。
5. 导出全部（AI 版可逆 / 人工版涂黑二选一），AI 版写组级映射（`group_id`），支持组级 rehydrate。
6. 组级 Verify：每文件残留检查 + 组内一致性 + 勾稽 + 号码合法性（§4.1 #34/#35 的增强）。

**关键改动点（file:line 级别，供排期评估）**

| 改动 | 位置 | 说明 |
|---|---|---|
| Job 增加共享会话/组字段 | `jobs.py:67-97` | `group_id`、`session` 由外部注入；`create()`（`:140-152`）增加参数 |
| 组管理器 | `jobs.py:133-167`（JobManager） | 新增 GroupManager 或扩展 JobManager |
| API 组接口 | `api.py:113-147` | `POST /api/groups`、`POST /api/groups/{gid}/files`、`POST /api/groups/{gid}/run`、`GET /api/groups/{gid}`、`POST /api/groups/{gid}/export`、`POST /api/groups/{gid}/verify` |
| 组级映射 | `vault.py:52-78` | `save_mapping(group_id, ...)` + `load_mapping(group_id)`；建议保留 per-job 映射，同时在组映射中合并 |
| 审计扩展 | `audit.py:20-37`（schema）、`:53-78`（append） | 增加 `group_id`、`file_role` 列（SQLite 迁移）；保持 HMAC 链（`:100-120`） |
| 金额策略 | `pipeline.py:180-205`、`surrogate.py:654-695` | 批级比例因子（按币种），所有金额乘同一因子；大写同步 |

| 前端 | `app/web/app.js` | 组控制台：文件列表+角色、共享映射面板、一致性/勾稽报告、批量导出 |

**勾稽引擎（P2）设计**

1. 单证类型识别（`doc_type_classifier`）→ 选择字段模板。
2. 字段抽取：优先表格（xlsx 单元格；PDF 需表格结构）→ 其次 `field_det` → 最后正则/实体。
3. 归一化：金额（币种+数值）、数量（数值+单位）、重量（kg）、号码（去空格/统一大写）、公司名（去括号/简称匹配）。
4. 执行 J1–J15 → 报告三态：`通过 / 不一致（阻断导出）/ 缺字段（提示）`。
5. 金额策略二选一：**批级比例缩放（推荐，保持勾稽）** vs 逐值 ±25%（现状，仅单文件给 AI 看）。
6. 报告落盘：组级 JSON + 页面展示；审计只记"检查项+结果"，不记原值（沿用 `audit.py:1-5` 的原则）。

**风险与对策**

- 组内文件顺序影响假值 → 改为"先全组检测、再统一决策"（见上表）。
- 组映射泄露 = 全批可还原 → 映射 AES-GCM 加密（复用 `vault.py:52-66`）+ 组级 TTL/一次性导出提示；`vault.wipe`（`:95-108`）扩展到组。
- 性能：扫描件 OCR 是瓶颈，组内建议并发解析限 2–3 个文件（`MAX_JOBS_IN_MEMORY = 24`，`jobs.py:665`）。

### 8.3 边界声明（建议写入产品文案/README）

1. **只做去标识化，不做匿名化**：换名/涂黑后仍可能通过组合信息再识别；产品不承诺"无法识别"。
2. **不做合规承诺**：不保证满足海关、外汇、出口管制、数据出境、GDPR/《个人信息保护法》等任何法规要求；用户需自行判断并咨询专业机构。
3. **换名件不可用于官方/法律用途**：报关、收汇、信用证交单、仲裁/诉讼证据必须使用原件。
4. **不协助规避监管**：不提供"洗单""改单"能力；HS/金额/数量/许可证等监管要素的换名明确禁止或默认涂黑。
5. **数据不出本机**：沿用产品既有设计（`127.0.0.1`、无外呼）；用户自行承担把成品上传外部 AI 的后果。
6. **不做解密/破解**：加密 PDF、带签名单证、受控数据（涉密）不在处理范围。

> 注：`packs` 计数为 `include` 后的总规则数（例如 `finance-cn` 19 = 自身 5 + common 14）。

**补充核验（独立计算）**：

- `91330200MA2AB1C2D3` 的 GB 32100 校验位应为 **J**（字符集 31 进制、权重见 §3.2），实际末位为 3 → **校验位非法但被识别**，证明 `cn.uscc` 未启用 `uscc_checksum`。
- 示例身份证 `330203199001011234` 的 GB 11643 校验位应为 **6**（实算），实际末位为 4 → 身份证规则未命中；该值恰好通过 Luhn（银行卡规则）→ 被误判为"银行卡号"（L3）。说明 18 位数字类规则需要**上下文/联合校验**，不能只靠单一正则。
- ISO 6346 示例 `CSQU3054383`：加权和 6185，6185 mod 11 = 3 → 与末位一致（合法），算法与 BIC 说明一致（附录 A#12）。
- AWB 示例 `999-1234567`：9991234567 mod 7 = 6 → 完整号码 `99912345676`（IATA unweighted modulus 7）。

**结论**：

1. 现有包对"个人/机构身份类"有一定覆盖，但对"贸易业务号码与金额"几乎为零。
2. 即使命中的条目也存在**未校验**（USCC）与**误分类**（身份证→银行卡）风险，P1 必须补校验器与上下文。
3. 该实验可在 P0 验收时复跑，作为"基线召回率"（当前 8/24 ≈ 33%）。

## 附录 D 号码校验算法速查（实现参考）

> 以下为文档级伪代码，落地实现见 §5.3；**不写产品代码**。

```text
# 1) ISO 6346 集装箱号（11 位）
LETTER = {A:10,B:12,C:13,...,K:21,L:23,...,Z:38}   # 跳过 11/22/33
sum = Σ value(char_i) * 2^i   (i=0..9)
check = sum mod 11; if check == 10 then check = 0
valid = (check == int(last_char))

# 2) IATA AWB（11 位数字）
check = int(first_10_digits) mod 7
valid = (check == int(last_digit))

# 3) USCC（18 位，GB 32100）
CHARSET = "0123456789ABCDEFGHJKLMNPQRTUWXY"
WEIGHTS = [1,3,9,27,19,26,16,17,20,29,25,13,8,24,10,30,28]
sum = Σ index(char_i) * WEIGHTS[i]   (i=0..16)
check = CHARSET[(31 - sum mod 31) mod 31]
valid = (check == last_char)

# 4) 身份证（18 位，GB 11643 / ISO 7064 MOD 11-2）
WEIGHTS = [7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]
CHECK   = "10X98765432"
valid = (CHECK[Σ digit_i * WEIGHTS[i] mod 11] == last_char)

# 5) IBAN（ISO 13616）
move first 4 chars to end; letters -> 10..35; if int(s) mod 97 == 1 then valid

# 6) 报关单号（18 位，无校验位，仅结构）
valid = match ^\d{4}(19|20)\d{2}[01IE]\d{9}$ and year <= current_year

# 7) SWIFT/BIC（ISO 9362）
valid = match ^[A-Z]{4}[A-Z]{2}[A-Z0-9]{2}([A-Z0-9]{3})?$ and country_code in ISO3166

# 8) HS（6/8/10 位，无校验位）
valid = length in (6,8,10) and 1 <= int(first_2) <= 97
```

**换名回写要点**：①②③④⑤ 类号码在生成假值后**必须重新计算校验位**；⑥⑦⑧ 类只做结构与长度保形。所有假值入库时标记 `synthetic=true`，导出件在页脚/水印声明"脱敏虚构数据，不得用于申报"。
