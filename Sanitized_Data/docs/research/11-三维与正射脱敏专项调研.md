### 2.3 真实正射：能处理 / 会拒绝 / 降级

**能处理（默认 `neutralized`、rasterio 可用、单页）**
- 任意大小单页 GeoTIFF（窗口流式）：保留源 dtype（uint8/uint16/float）与 1/3/4+ 波段；DEFLATE + tiled + 内部金字塔。
- 常见源 CRS（EPSG/WKT）：真实 Geo 结构剥离 → LOCAL_CS 本地任意 CRS（GIS 可打开、无真实坐标）；随机平移 + 旋转；参数可还原。
- 成品元数据全剥（Geo/EXIF/GPS/XMP/IPTC/ICC/描述/设备/版权），派生 sidecar 全删，导出后双重复检。
- 只有 Geo 标签、无 OCR 文字的正射：可「仅清理」导出；人工框选补漏可用。
- 预览走降采样，大图不整图解码。

**会拒绝**
- 未装 rasterio 且像素 > 约 1.79 亿：中文 `ParseError`（提示装 rasterio/切图）。
- 导出后仍有真实 CRS/EPSG/源 tiepoint/RPC/ICC/EXIF：`ExportError`，成品删除。
- 无实体且无任何可清理目标：正常业务拦截「没有需要隐去的内容」。

**降级（有显式 warning，不静默）**
- 多帧 TIFF → Pillow 回退：逐帧剥离、**不做中性化**。
- 未装 rasterio/pyproj 或 rasterio 打不开 → Pillow：只剥离；16bit/多波段/金字塔降级为 8bit RGB/LZW。
- 单页非 8bit RGB 的「换名文本」→ 退化为涂黑（保持 dtype/波段）。
- 大图 OCR/扫描基于降采样预览：条码/小字可能漏检 → warning 提示人工复核。
- 源 JPEG-in-TIFF → 重编码 DEFLATE（无损但体积可能变大）。
- **Pillow 路径 TIF Orientation 未转正（连 warning 都没有）**。
- 旋转 geotransform 写 `ModelTransformationTag`：QGIS/ArcGIS 可开，个别旧工具可能提示。

### 2.7 对架构承载正射后续增强的观察

1. **rasterio 可选依赖模式已验证，建议保留**：模块级 try/except + 函数内惰性导入，未装时 Pillow 降级 + warning；台账（requirements/`app.spec`/离线 wheel/sha256）齐全。代价是**双路径长期并存**——Orientation 缺口正是 Pillow 路径漏跟契约的例子；建议每条新能力显式写「rasterio 路径 / Pillow 路径」行为矩阵并双测。
2. **内存模型可扩展但未封顶**：导出 2048 窗口 + 256 分块；40Mpx 以内整帧读取做 OCR 预览（约 120MB 可接受），超过则降采样。DESIGN 的 <1.5GB / <90s 没有真实基准，**先补 P2 实测再对外承诺**。
3. **UI/框选架构可行**：`render()` 降采样、rect 在导出窗口内绘制，大图不需整图内存；缺的是 geo_mode 暴露、中性化状态提示、TIF 专项 e2e。
4. **verify 分层合理但 TIF tag 证据链只有一层**：tag 级复检依赖 `TiffParser.export` 必执行；若将来有绕开该路径的导出（新格式/批量工具），`pipeline.verify` 对 TIFF tag 是盲的。多帧复检只看首 IFD，做多帧中性化时必须扩全帧。
5. **可还原只到「参数+成品→原图像素坐标」**：`rehydrate.py` 目前只处理文字映射；若对客户承诺「可还原正射」，需补坐标还原 CLI/说明（0.5–1 人日）。
6. **自研 IFD 扫描器是双刃剑**：支撑无 rasterio 时的剥离/复检，但绕开 GDAL，对 COG mask/SubIFD/私有标签未验证；建议 rasterio 为真实文件的 source of truth，`scan_tiff` 只作降级/复检辅助。

### 3.3 四格式实测结论

- **OBJ**：7 个文本 Block；识别 3 实体（图幅号/控制点号/坐标系名）→ 换名/涂黑均可、残留 0、verify 通过；顶点 `500123.456…` → `-1/-1/-1…`；**`mtllib 项目模型.mtl`、`o/g Tile_+000_+000_L20`、`usemtl Material_0`、项目名原样**；成品无 .mtl/贴图。
- **PLY ascii**：2 实体清掉、顶点减中心；header 写入 `█`（UTF-8 多字节）→ 成品 header 变非 ASCII，严格读取器可能拒绝。
- **PLY binary**：无命中时逐字节一致；**命中 black 时 header 变长 → 用输入 `data_offset` 写回导致整体错位：成品 header 被顶点字节覆盖、几何损坏、重解析报「PLY 头部缺少 end_header」，但 `pipeline.verify` 仍放行**。根因是 `mesh_parser.py:979-1015` 使用输入 `vertex_offset` 写回；同长度 surrogate 则正常。
- **STL**：头 80B 全 NUL、84B 后几何逐字节一致；**头不含规则词时（项目/软件/日期）整段保留且 verify 通过**；ASCII 分支等长空格未单独实测。
- **GLB**：JSON chunk 716B→716B、仍可解析；`CGCS2000` 被替换为 8 个半角空格；**BIN 60B 逐字节一致（含假 JPEG 字节）**；`accessors.min/max` 仍保留原始大地坐标数值；内嵌图不抽取、不写 `embedded_media`。

| 2a | OBJ 顶点改回大地坐标 | ✅ 放行 | 几何不参与 verify |

| UI | 预览 `kind` 只有 raster/flow；mesh 为 flow 文本流；`render()` 返回 None | `kind="scene"`；贴图资产清单/2D 对照；3D 拾取或退化为贴图矩形框选 |
| vault | AES-GCM + `extra` 透传；TIF `geo` 已用 | `geo3d` 参数段；参数 TTL/一次性策略 |
| verify | 只查文本/meta/geo_tags/视觉 IoU；6 类三维篡改放行 5 类 | L1–L5（见 §4.5）；`unverifiable` 必须显式 |
| rules | mesh scope 仅 13 条（common 9 + geo-cn 4）；`cn.geo_decimal` 不含 mesh | 项目名/软件名/版权方/瓦片名/MTL 名/metadata.xml SRS 规则；数值规则 |

## 4 基于当前架构，以后能不能做

### 4.1 架构与一次 job 的调用链

```
app/web（投放台 → 识别中 → 对照台 raster<img>/flow DOM → 交付台；框选 rect 归一化）
   │ HTTP 127.0.0.1（同源校验）
api.py（/upload /jobs /preview /render /mark /entities /export /file /audit /health）
   │
jobs.py（JobManager：1 job = 1 文件 + 后台线程状态机 + 进度/取消/淘汰/导出/预览/映射）
   │
pipeline.py（detect → merge → decide(Session) → export(parser.export) → verify(重解析)）
udm.py（Document / Page / Block / Span / Entity / Decision / VisualMark）
   │
registry.py（Parser/Detector/Replacer 协议 + 插件自动导入）
parsers/（pdf docx xlsx image tiff text mesh）
   │
vault.py（AES-GCM 映射 + extra["geo"]）· audit.py（链式审计）· mediascan.py（页面图像扫描器）
georef.py（正射地理参考/中性化数学/复检）
```

**关键抽象及其隐含假设**（这是「能不能做」的根因）：

| 抽象 | 隐含假设 | 对三维/正射的意义 |
|---|---|---|
| `Document`（`udm.py:80-88`） | 一个 Document = 一个物理文件；`fmt` 单值 | 正射完全适配；三维整包（OBJ+MTL+贴图、OSGB 目录、3D Tiles 目录）无表达位 |
| `Page`（`udm.py:71-76`） | 2D 页面 width/height + blocks | 正射 1 页 1 帧适配；三维只能伪造 A4 |
| `Block`（`udm.py:48-56`） | kind 只有 text/table/image；主载荷 text | 贴图/材质/顶点/瓦片/节点无 kind |
| `Span`（`udm.py:118-140`） | 只有文本区间或页面矩形 | 无法表达顶点区间/纹理 UV/tile id/点索引 |
| `Parser`（`registry.py:24-45`） | `parse(path)->Document`、`export(out_path)->ExportResult`、`render(page)->PNG`；`can_render` 二态 | 无目录/整包、无多资产输出、无 3D 渲染 |
| `Detector` | 实际只遍历文本块 | 贴图须先变成 image 文档才能复用规则 |
| `Replacer` | 策略基于字符串值 | 几何变换不是「值替换」，需新的 Plan 类型 |
| `Job`（`jobs.py:82-121`） | 单 path、单 parser、单 doc、按页预览、单文件导出 | 整包任务无状态位 |
| `Verify`（`pipeline.py:635-758`） | 只接受单成品路径，只查文本/meta/视觉 | 目录包无法验证；几何/贴图/点云无验证语义 |
| `PreviewDoc`（`CONTRACT.md:222-241`） | kind 只有 raster/flow | 3D 需新 kind/协议 |
| UI 对照台（`app.js:1012-1022`） | raster img / flow DOM 二选一；框选是 2D 归一化矩形 | 3D 场景拾取/标注/相机无落点 |

### 4.2 可复用内核（约 60–70%）

| 能力 | 复用方式 |
|---|---|
| 规则引擎（YAML/编译/优先级/scope） | 加 scope 值即可（mesh 已有 13 条；新增 tileset/pointcloud） |
| 检测器框架（regex/dict/ner/joined/financial/trade/pipl/table/numeric） | 贴图 OCR 出来的文字直接走同一批规则 |
| 替换/脱敏策略 + Session 实体图 | 贴图内文字替换直接复用 |
| OCR + 图像/视觉扫描内核（`image_parser`/`mediascan`/`visual_targets`） | 抽出贴图/内嵌图 → 同一套 OCR + 人脸/证件/车牌/码/印章扫描 + 涂黑 |
| 加密映射库（AES-GCM + extra） | 文字映射 + `geo` 参数已有；新增 `geo3d` 即可 |
| 审计链 / 任务框架 / 进度取消 / 交付编号 / 双轨导出 | 与格式无关；补「资产清单哈希」与目录/zip 支持 |
| 2D 对照台交互范式 | 贴图对照可直接复用；3D 场景需新渲染路径 |
| 离线打包/CI/部署 | 同仓第二个 spec/构建目标即可 |

**被硬编码为「文本 + 位图 + 单文件」的关键点**（14 条，证据见 `_survey/architecture.md §3.2`）：单 Document 单文件、Page 2D、Block 仅三种 kind、Span 仅两种寻址、Parser 单文件进出、render 只有页面 PNG、Job 单路径单扩展名、preview 仅 raster/flow、verify 只接受单成品、上传单文件 512MB 上限、mesh 被文本化、`can_render=False` 即无预览、无容器内资产抽取层。

### 4.3 正射：原位扩展（A 路线），不需要新抽象

| 能力 | 落点 | 新抽象 | 人日 |
|---|---|---|---|
| 多帧中性化 | 扩 Pillow 导出/分帧 rasterio 写法 | 无 | 2–3 |
| 坐标取整/量化、按密级降采样 | `georef` 参数 + 重采样（已有 `YINZHAN_TIFF_*` 框架） | 无 | 2–3.5 |
| 4+ 波段语义、16bit 换名限制 | tiff_parser 内 | 无 | 1 |
| 大图预览/框选体验/内存 | 调窗口/预览参数 + 回归基线 | 无 | 0.5–1 |
| 验收自动化（rasterio 断言进回归） | `app/tests` 扩展 | 无 | 1 |
| 敏感地物自动识别 | 明确不做（DESIGN 本身要求人工框选），P1 只做体验 | 无 | 0 |

**判断**：正射 P1 是现有域收口，**不应成为立项/拆项目的理由**。

### 4.4 三维：需要 5 类新抽象（B 路线）

| 新抽象 | 形态（供 CONTRACT v4 讨论） | 服务的能力 |
|---|---|---|
| **Package/Asset** | `Document.assets[]`（role: geometry/material/texture/metadata/tile；path/sha/handled）；`Parser.parse_package/export_package`；`Job.root` + `output_kind`（file / dir / zip 三态）；`ExportResult` 支持目录/manifest；上传支持 zip 或按路径选目录 | OBJ+MTL+贴图、GLB 内嵌图、3D Tiles 目录、OSGB 目录 |
| **Scene/TileTree** | `Document.scenes[]`（根 transform/CRS/瓦片树）；tile 挂 assets | 3D Tiles、OSGB |
| **PointCloud** | 新 `format_id=pointcloud` + 点云几何中性化 Plan（平移/旋转/量化/抽稀/加噪）+ VLR/CRS 清理 + header 重算 | LAS/LAZ |
| **GeometryPlan / vault geo3d** | 几何变换参数结构（translate/rotate/quantize/decimate/noise/seed/src_crs），走 `doc.extra["geo3d"]`→vault 同一 AES-GCM 通道；human 模式不存 | 所有三维几何中性化 |
| **结构化 Verify + scene 预览** | `verify` 增加可注册复检器 + `structural/unverifiable` 字段；`PreviewDoc.kind="scene"` + 前端离线 WebGL（最小可用可为「资产清单+贴图 2D 对照」） | 交付质量与责任边界 |

**三维各能力落点**（A=原位可做；B=需新抽象但同仓域模块可做；C=当前架构不适配/需独立域甚至独立项目；D=本阶段不做）：

| 能力 | 落点 | 人日 `[估]` | 风险 |
|---|---|---|---|
| OBJ + MTL + 外部贴图 | **B** | 3–4 | 中 |
| GLB 内嵌图 | **B** | 4–6 | 中高 |
| GLB/STL 几何中性化 | **B** | 2–4 | 中 |
| 3D Tiles | **C/B（域内深子项）** | 5–7 | 高 |
| LAS/LAZ 点云 | **B** | 4–5 | 中 |
| OSGB 纹理/几何 | **C / D** | 15–23 | 最高 |
| 3D 预览（完整场景） | **C（前端新域）** | 最小 2–3；完整 8–15 | 高 |
| 空三/控制点/照片批量 | **B（可后置）** | 2–3 | 低中 |
| 结构验证门禁 | **B（先于其它三维能力）** | 2–3 | 中 |

> 结论：三维中真正「不适配」的只有 **OSGB 容器**与**完整 3D 交互预览**；其余可在同仓独立域模块内完成。**新增 5 类抽象的成本主要在 Package/Verify，而不是每个格式的解析器**——抽象立好后，OBJ/GLB/3D Tiles/LAS 可按格式并行。

### 4.5 验证责任：三维不能沿用现有 verify 语义

现有 `pipeline.verify` 的核心承诺是「重解析成品还能找到原文就拒绝交付」。该语义对**文本**有效，对**几何/贴图/内嵌图/点云/文件结构**无效（本次实测 6 类篡改放行 5 类）。三维落地必须新增五层（写进 CONTRACT，不能静默放行）：

| 层 | 做法 | 失败处理 |
|---|---|---|
| L1 结构断言 | 重解析成品：GLB JSON 可解析、chunk 长度/对齐、accessor/bufferView 边界合法、mesh 索引在顶点范围内、包围盒有限；tileset JSON schema + 所有 `content.uri` 存在；LAS header point_count/bbox 与点集一致 | 不通过 → 删成品 + `VerifyError` |
| L2 字节不变性 | 未处理的 BIN/chunk/tile/贴图与输入哈希逐一比对；「本应不变」的字节变了即失败 | 同上 |
| L3 贴图重扫 | 抽取成品全部贴图 → OCR/视觉扫描；残留必须为 0；扫描失败/跳过必须显式声明 | 残留>0 或未声明 → 阻断；skip 需二次确认 + 审计 |
| L4 人工抽样声明 | 每批 ≥20 张贴图人工抽检；API/UI 记录 `manual_review` | 无记录 → 阻断（或只允许导出「待复核」水印版） |
| L5 不可验证声明 | 导出记录 `unverifiable: []`（如点云轮廓反推、OSGB 几何边界） | 缺失字段视为门禁缺陷 |

## 5 要不要单独开一个项目（核心决策）

### 5.1 直接回答

| 问题 | 结论 | 理由 |
|---|---|---|
| 正射脱敏要单独开项目吗？ | **不要** | 已在当前架构内完成 P0；剩余 P1 是同一解析器的原位增强（6–10 人日），无新抽象；单独开项目只会重复 `georef/tiff_parser/vault/规则/UI` |
| 三维脱敏要单独开项目吗？ | **现在不要** | 需要 5 类新抽象 + 目录任务 + 3D 预览 + 结构验证，但**可隔离在同仓独立域模块**；规则/检测/OCR/映射/审计/任务/UI 外壳可复用 60–70%；当前无三维客户合同、无样例、无团队证据，拆分门槛（§5.4）均不满足 |
| 那三维怎么立项？ | **同仓独立域模块（B）** | `yinzhan/geo3d/`（或独立顶层包）+ 可选依赖 `requirements-3d.txt` + 功能开关 `YINZHAN_3D` + 独立发布包/构建目标 + 独立测试门禁；主产品回归与门禁不被污染 |
| OSGB 怎么办？ | **本阶段 D（不做）**；出现真实合同/样例后作为**业务子项目 C**触发 | OSGB 无公开规范、无样例、无查看器、LGPL 血缘、15–23 人日且不能承诺「可打开」；即使拆代码项目也不能消除这些风险。可先用 Apache-2.0 转换器（fanvanzh/3dtiles）做「OSGB→3D Tiles」预研，客户接受交付格式再谈 |

### 5.2 四条路线对比

- **A 同仓同应用继续做**：所有能力塞进现有「一文件一任务」应用，同一发布包。
- **B 同仓独立域模块（推荐）**：共享内核 + 可选依赖 + 功能开关 + 独立发布目标/独立测试门禁。
- **C 独立仓库/独立项目**：新建项目，复制或引用核心（submodule/私包），独立产品线/UI/发布。
- **D 本阶段不做三维**：只做正射收口；三维保留有限支持并如实标注。

| 维度 | A 同仓同应用 | **B 同仓独立域模块（推荐）** | C 独立项目 | D 不做 |
|---|---|---|---|---|
| 技术契合 | 正射 ★；三维 ✗（页面/单文件模型每加一能力打补丁） | 正射 ★（走 A）；三维 ★（新抽象隔离在域内） | 三维 ★；正射 ✗（重复实现已有 `georef`/tiff） | — |
| 复用度 | ★（100% 复用但把复杂度灌入内核） | ★（规则/检测/OCR/映射/审计/任务/UI 复用，估 **60–70%**） | △（复制/引用，长期漂移；正射 0 复用） | ★ |
| 交付发布 | ★ 一个包；但三维依赖/UI 让所有用户买单 | ★ 主包不变；三维独立包/组件，按需安装 | △ 两条发布链/CI/签名/更新 | ★ |
| UI 与交互 | ✗ 对照台二态无法承载场景 | ★ 共享外壳 + 新增 3D 视图组件（两个入口） | ★ 自由但用户要装两个产品 | ★ |
| 验证与责任 | ✗ 几何不可验证却混入同一 verify 门禁，稀释出口自检公信力 | ★ 域级门禁 + `unverifiable` 显式声明；主门禁不变 | △ 独立门禁但共享内核回归要两边同步 | ★ |
| 工期（剩余） | 正射 6–10 + 三维 15–25 + 3D 预览 8–15（全部耦合主链路风险） | 正射 6–10 + 域模块 10–16（含最小资产对照） | 正射仍 A 6–10 + 新项目 25–45（含重搭内核/UI） | 正射 6–10；三维 0 |
| 团队 | 1–2 人可维护（知识面要求极高） | 1 人可起（域内自包含），后续 2 人 | ≥3 人（前端+引擎+构建/测试） | 现有团队 |
| 商业定位 | 「通用门」被稀释 | ★「跨格式+地理/三维+可举证」可独立报价 SKU（测绘/应急/审图） | ★ 可做垂直产品，但品牌/销售双线 | ★ 聚焦律所/医院/财务首批场景 |
| 维护 | ✗ 三维依赖/回归拖慢主版本 | ★ 依赖隔离、开关可关、失败不拖垮主产品 | △ 双仓同步成本 | ★ |
| 风险 | 高：主产品发布被三维构建/回归阻塞；verify 语义被污染 | 中：需先立 Package/Verify 协议；域内二进制风险可控 | 高：重复建设、接口漂移、OSGB 法律/规范风险仍在 | 低：可能错失测绘客户窗口 |

**推荐**：**正射 A；三维 B + 分期；OSGB D（条件触发 C）；3D 预览只做「最小可用」（资产清单 + 贴图 2D 对照 + 可选网格查看）。**

### 5.3 为什么推荐 B 而不是直接开 C

1. **架构代价最小**：正射已在现有内核闭环；三维真正缺的是 5 类抽象，放进同仓独立域模块可**隔离复杂度**，同时保住 60–70% 既有内核复用，避免另起炉灶重复实现规则/OCR/映射/审计/UI。
2. **验证责任可分**：现有 verify 的承诺是「重解析成品找不到原文才允许交付」；三维几何/贴图不可像素级复检，混入同一门禁会稀释主产品「出口自检」的公信力。域模块可设自己的「结构断言 + 贴图重扫 + 人工抽样 + `unverifiable`」门禁，主门禁保持 F1–F19 强度。
3. **商业与发布可控**：测绘/倾斜摄影是独立客群与独立 SKU；B 允许主产品不带三维依赖（不背 +100MB 包）与三维 UI 资源，按需安装/独立发布包；正射用户零成本。
4. **C 在需求未验证前承担双仓/双团队/双发布成本**，且 OSGB 无规范风险不会因拆项目消失；先 B 孵化、用真实客户与数据验证，再考虑拆分更稳。

### 5.4 什么条件下才值得「拆项目」（C）

**满足 ≥3 条硬条件**再开独立项目（否则保持 B）：

| # | 触发条件 | 阈值 | 数据来源 |
|---|---|---|---|
| T1 | 三维域代码/依赖体量 | 域代码 > 10,000 行且独立依赖解压 > 200MB，或主安装包因三维 +>120MB | cloc / PyInstaller 产物对比 |

### 5.5 合规边界（决定「要不要做测绘行业产品」的关键外部变量）

**事实**（自然资源部办公厅《关于推进地理信息保密处理技术研发和服务工作的通知》，自然资办发〔2021〕22 号，[原文](https://gi.mnr.gov.cn/202102/t20210219_2612294.html)）：
- 国家支持针对**矢量、栅格、三维模型、实景数据**等涉密地理信息研发「对空间位置、精度、属性内容及其相互关系全部或部分进行保密处理」的技术；处理后结果应具备**不可逆性**。
- 根据《测绘地理信息管理工作国家秘密范围的规定》，**国家认定的地理信息保密处理技术算法及参数为国家秘密**；技术须经自然资源部会同国家保密局商军队部门**认定后使用**；**擅自利用未经认定的技术（算法及参数）对地理信息空间位置、精度、属性进行处理，不改变原有密级，不能作为定密、密级变更、解密的依据**。
- 部里建立保密处理技术目录（服务单位/处理范围/领域）；目录内服务单位无偿提供及时、安全、可靠的服务，不得复制、留存涉密数据及处理结果；未纳入目录的技术**仅可在本法人单位内部使用**；经保密处理的地理信息如需公开使用，应依法进行**地图审核**。

**对本项目的含义**：
1. 我们做的「随机平移+旋转+本地 CRS / 三维坐标中性化」是**产品级降密/去标识**，**不是**国家认定的「地理信息保密处理技术」。对**涉密测绘成果**，不能宣称「已脱敏/可公开/合规」；它不改变原密级，也不能作为定密/解密依据。
2. **「可还原」模式（D2 已批准）仅适用于内部 AI 使用场景**；若客户要求不可逆/对外公开，应使用 strip/不可逆模式，并提示需按国家规定处理。
3. 面向测绘/实景三维客户销售时，可能涉及**测绘资质、保密处理技术认定/目录服务、地图审核**等门槛；需法务与资质评估，必要时与目录内单位合作或只做「非涉密内部数据」场景。
4. 因此，若「三维+正射」要成为独立**测绘行业产品线**，它是**业务/合规立项问题**，不只是代码项目问题；但这不需要现在拆代码仓库——先以 B 形态服务非涉密客户，合规路径另行评估。

> 本节为事实梳理与风险提示，不构成法律意见；对外话术必须由法务/合规确认。
