## 0. 结论摘要

| # | 结论 | 关键证据 | 影响 |
|---|---|---|---|
| C1 | **当前产品完全没有条形码/二维码识别或打码能力** | 全仓库 `条码/二维码/barcode/QRCode/zxing/zbar` 关键字 **0 命中**；图像/PDF/TIFF 只做 OCR 文本与红章/手写签名视觉检测；DOCX/XLSX 对内嵌图片只告警 | 码里承载的税号、金额、校验码、链接、主体信息**会随图原样外发** |

| C3 | 依赖前提需要修正：**`cv2.barcode` 不需要 opencv-contrib** | 官方 4.8.0 公告：barcode 从 `opencv_contrib` 移入 `objdetect`；实测临时 venv 安装 `opencv-python-headless==4.13.0.92`（即 requirements 声明包）后 `cv2.barcode`、`cv2.QRCodeDetector`、`QRCodeDetectorAruco`、`QRCodeEncoder` 全部可用 | **不必须改 OpenCV 依赖**；真正要决策的是"是否新增 zxing-cpp 以覆盖 DataMatrix/PDF417/Aztec 与更稳的 1D 解码" |
| C4 | 选型推荐：**zxing-cpp 为主检测/解码引擎，cv2.QRCodeDetector(Aruco) 为第二意见兜底**；不引入 pyzbar | 实测 zxing-cpp 在一次 A4/300dpi 页面中 6/6 检出并解码（QR+DataMatrix+PDF417+Aztec+EAN13+Code128），147.8ms；cv2 只能解出 QR 与 EAN13（1D 整页 Code128 漏检）。zxing 对反色、0.25× 缩小、旋转/透视/遮挡均成功；样例页误检 0 | 一套依赖覆盖全部主流码制；代价：新增 1 个 Apache-2.0 wheel（Windows x64 约 1.0MB）+ 契约/依赖/打包更新 |
| C5 | 策略推荐：**默认一律打码，不做内容敏感性判断**；解码结果仅用于审计/提示/白名单例外，不作为"是否打码"依据 | 发票二维码含税号/金额/校验码等要素（查验平台与行业解析实现均如此），扫码语义无法可靠判断；检测到框但解码失败（遮挡/低对比）也必须打码 | 最保守、可解释；1D 商品条码的"白名单例外"留作决策点 D3 |
| C6 | 打码方式：**整码 + 静区外扩后实心涂黑（多边形填充）**，不是模糊/马赛克；PDF 用 redaction 真删除 | 实验：PDF `add_redact_annot(fill=(0,0,0)) + apply_redactions()` 默认 `images=PDF_REDACT_IMAGE_PIXELS` 会把被覆盖的图像像素涂黑（部分覆盖也有效）；位图 `fillPoly + JPEG q92` 后不可解码；DOCX/XLSX zip 级替换 media 后不可解码 | 与现有"涂黑 ≠ 画黑框"红线一致（DESIGN.md:238-258） |

**一句话方案**：新增独立 `barcodes.py` 检测模块（zxing-cpp 主 + cv2 兜底，原分辨率/300dpi 渲染、多尺度、反色、旋转均尝试），在 Parse 阶段把每个码转成带 quad 矩形 span 的实体（默认 `black`），复用现有 image/pdf/tiff 导出链路做实心涂黑；DOCX/XLSX 内嵌图片用 zip 级 media 替换；Verify 增加"对成品重跑检测 + 解码，必须不可再解码"的硬门。

| 参数 | 值 | 位置 |

实测（A4/300dpi 页内放 8 个不同模块尺寸的 QR，附录 B.2）：

| 检测图长边 | 等效分辨率 | `cv2.QRCodeDetector` 检出/8 | `QRCodeDetectorAruco` 检出/8 | 解码/8 |
|---|---|---|---|---|
| 3508（原图） | 300dpi | 7 | 7 | 7 |
| 2400（`OCR_MAX_EDGE` 等效） | 205dpi | 4 | 7 | 5 |
| 1754 | 150dpi | 4 | 7 | 6 |
| 1240 | 106dpi | 1 | 6 | 3 |
| 992 | 85dpi | 0 | 5 | 3 |

> 表头"解码/8"为 `QRCodeDetectorAruco` 的结果；`cv2.QRCodeDetector` 解码数整体更低（见附录 B.2）。

> 结论：**条码检测不能吃 OCR 的缩放图**。`2400` 就丢 3/8，150dpi 丢 2/8，106dpi 几乎全丢。检测必须在原图/300dpi 渲染或分块上做。1D 码更明显：同一实验里只有 2/3 的 EAN-13 能解，最小模块那一档直接丢。

## 2. 需求与目标

### 2.1 用户需求与威胁场景

| 场景 | 码里通常有什么 | 外发风险 |
|---|---|---|
| 增值税发票 / 数电票截图、扫描件 | 发票代码、号码、金额、开票日期、校验码等要素（扫码可回填查验信息） | 税号/金额/票号随图给到模型或对家 |
| 营业执照 / 资质证照 | 主体名称、统一社会信用代码、登记信息、公示系统跳转链接 | 主体身份与关联信息 |
| 收款码 / 付款码 | 商户号、订单号、金额、收款人标识 | 账户/交易信息 |
| 健康码 / 检测码 / 票码 / 通行码 | 个人标识、时间、地点/票号 | 个人行踪与身份 |
| 报关单 / 物流面单 / 商品条码 | 报关单号、运单号、SKU/EAN 号 | 业务单号与商品信息 |
| 名片 / 合同附件二维码 | 姓名、电话、邮箱、vCard、公司主页 | 个人信息 |

### 2.2 目标（本方案范围）

1. 从 **位图（PNG/JPG/BMP/WEBP）**、**PDF 页面**、**TIFF 多帧**、**DOCX/XLSX 内嵌图片**中识别 1D 条码与 2D 码；
2. 默认可**不可逆打码**（实心涂黑整码 + 静区），并保证成品**不能再被解码**；
3. 导出自检（Verify）对码类残留**硬拦截**；
4. 全程离线、CPU、Windows、与现有 PyInstaller 打包兼容；不改动联网行为（CONTRACT.md:5-10、230-236）。

### 2.3 非目标（本批）

- 不做"扫码内容语义判断"来决定是否打码（见 §3.3、D2）；
- 不做 3D 贴图内码（P3/后续）、不做视频码；
- 不解决"手机拍摄极端畸变/强反光/折叠残缺码"的 100% 召回——以"高召回 + 人工复核 + Verify 硬门"兜底；
- 不改变现有 OCR/文本检测语义。

## 3. 技术选型

### 3.1 候选方案

| 方案 | 能力 | 依赖 / 联网 | 结论 |
|---|---|---|---|
| **A. `cv2.QRCodeDetector` / `QRCodeDetectorAruco` + `cv2.barcode.BarcodeDetector`** | QR 检测+解码+多码+透视；Aruco 版对低分辨率更稳；1D 支持 EAN-8/13、UPC-A/E、Code-128/39/93、ITF 等（官方支持列表） | 已随 `opencv-python-headless>=4.8` 提供；无需联网 | **保留为兜底/第二意见**；2D 只覆盖 QR，1D 实测不稳 |
| **B. zxing-cpp（推荐主引擎）** | QR/MicroQR/RMQR、DataMatrix、PDF417/MicroPDF417/CompactPDF417、Aztec/AztecRune、EAN/UPC/Code128/39/93/ITF/Codabar 等；多码、旋转、缩小、反色、位置四边形、错误信息、离线生成测试码 | `pip install zxing-cpp`，Windows x64 wheel 约 1.0MB；Apache-2.0；Python ≥3.9；无外呼 | **推荐**：一套覆盖全部主流码制，1D 明显更稳，速度快 |
| C. pyzbar | 1D + QR | 依赖 zbar 动态库（Windows wheel 自带旧版 zbar）；LGPL-2.1（动态链接需注意合规）；需 VC++ 2013 运行库；项目 2022 年后基本停更，PyPI 未声明 3.11+ | **不推荐** |
| D. WeChatQRCode（cv2 内） | QR 检测（DNN 模型） | 需要额外 caffe 模型文件；体积/分发成本上升 | 不采用（收益不抵成本） |

**实测（本机，附录 B.2 / B.4）**

| 测试 | zxing-cpp | cv2 |
|---|---|---|
| A4/300dpi 页内 6 个码（QR+DataMatrix+PDF417+Aztec+EAN13+Code128） | **6/6 解码** | QR 1/1；1D 只解出 EAN13；DataMatrix/PDF417/Aztec 0 |
| QR 变形 12 项（旋转 90/180/15/45°、透视、中心 logo 20%、角部裁 25%、模糊 σ=1.5、JPEG q50、反色、0.25× 缩小） | **12/12 解码** | 10/12（反色失败；0.25× 检出但无文本） |
| A4/300dpi 整页耗时（多码页） | 147.8ms | QR 427.2ms（decode）；1D 14.5ms |
| A4/200dpi 整页耗时 | 79.2ms | QR 208.7ms |
| 无码样例误检（合同 2 页 @200/300dpi） | 0 | 0（QR 检测） |
| 码制生成（离线造测试集） | `create_barcode` 支持 QR/DataMatrix/PDF417/Aztec/MicroQR/EAN13/Code128/Code39/ITF 等 | `cv2.QRCodeEncoder` 只造 QR |

> 补充：`cv2.barcode` 的默认 `downsamplingThreshold=512`（官方文档：小边超阈值时先缩放，调大可提高精度但更慢；默认 detector scales `[0.01,0.03,0.06,0.08]`）。实测把阈值调到 1024 时 EAN13 召回 3/4、512 时 3/4、64/2048/4096 反而 0–1/4——**1D 对尺度敏感，不能只跑一次**，需多尺度 + 真实样例调参；这也是推荐 zxing 作主引擎的原因之一。

### 3.3 策略建议：默认一律打码，不做内容判断

**推荐策略：检出即打码（unconditional redaction）**；解码只用于"审计/提示/白名单例外"，**不作为是否打码的依据**。

| 理由 | 说明 |
|---|---|
| 码语义无法可靠判断敏感性 | 同一张二维码可能是发票（税号/金额/校验码）、收款码（商户/订单）、健康码（个人标识）、无害官网链接；只看 payload 前缀/域名无法覆盖全部票种与业务系统版本 |
| 解码失败 / 部分遮挡仍可能泄露 | 实测：中心 logo 遮挡 15–20% 时 cv2/zxing 可能"检出但解码空"，但**残缺码仍可能被其他工具/更高版本算法读出**；以"解码成功"为打码条件会直接漏打（实验 B.2/B.4） |
| 发票/营业执照/报关单二维码承载主体与金额信息 | 发票二维码可回填发票代码/号码/金额/开票日期/校验码（查验平台要素）；营业执照二维码指向经营主体登记信息与公示系统；这些正是"外发给 AI/对家"最敏感的字段 |
| "宁可多涂不可漏"与现有产品红线一致 | CONTRACT.md:143-148 要求破坏性重写、不得静默丢弃；DESIGN.md:238-258 明确"画黑框不算脱敏"。默认全打是唯一可解释的安全基线 |
| 1D 商品条码业务上可能不敏感 | EAN/UPC 商品码本身通常只是商品编号，**仍建议默认打码**；若确有"保留商品码"的业务诉求，用可选白名单例外（按码制+payload 校验位/前缀配置），且默认关闭（D3） |
| 打码误伤成本可接受 | 多涂一处码通常只是观感损失；漏打一处码可能是税号/金额随图外发，两者风险不对称 |

**落地规则（建议写进实现）**：

1. 检出（含"检出但解码空"）→ 一律生成 `black` 决策；
2. 解码结果不参与决策；仅在审计里记"类型/数量/是否解码成功"（D4）；
3. 白名单例外（若未来开启）必须**按码制 + 结构化校验**（如 EAN/UPC 校验位通过且前缀属于商品码段），且界面上逐条可见、默认关闭；
4. 无法判断时**打**，不打是例外而非常态。

### 3.4 选型结论

1. **主引擎：zxing-cpp（≥3.1，钉死小版本）**——覆盖全、1D 稳、快、Apache-2.0、wheel 小；`read_barcodes(img, formats=..., try_rotate=True, try_downscale=True, try_invert=True, return_errors=False)` 默认已包含旋转/缩放/反色尝试；返回 `format/text/position(4 点)/orientation`，正好喂 UDM 的 rect/quad span。
2. **兜底：cv2.QRCodeDetectorAruco + cv2.barcode**——零新增依赖（`opencv-python-headless>=4.8` 已有），在 zxing 不可用/不支持某畸形码时补位；两引擎结果按 IoU 合并，打码取并集（宁多涂不可漏）。
3. **不引入 pyzbar**（DLL/许可/维护风险）。
4. **OpenCV 依赖不必须改**（见 §1.4）：保留 `opencv-python-headless>=4.8`，建议顺手把开发机实际安装的 `opencv-contrib-python/opencv-python` 对齐 requirements，避免"本机能跑、干净环境不能跑"。
5. **契约变更**：CONTRACT.md 第 0 节"可用三方库"需新增 `zxingcpp`，并且按 CONTRACT.md:1-3"改动契约必须先改本文件"的要求先改契约；`desktop/app.spec` 需补 zxingcpp 收集（当前只 `collect_submodules("yinzhan")` + `collect_all("rapidocr","onnxruntime")`，见 `app.spec:27-35`）。

## 4. 打码与集成设计

### 4.1 检测层（新增 `app/server/yinzhan/barcodes.py`）

```text
detect_barcodes(image_bgr_or_gray, *, source_dpi=None) -> list[BarcodeHit]
BarcodeHit = {kind: "qrcode"|"barcode", format: str, payload: str|None,
              quad: [(x,y)×4] 或 bbox, orientation: int, engine: "zxing"|"cv2"}
```

要点：

1. **引擎顺序**：zxing `read_barcodes`（全格式）→ cv2 `QRCodeDetectorAruco.detectAndDecodeMulti` + `cv2.barcode.BarcodeDetector.detectAndDecodeWithType`（仅当 zxing 不可用或未覆盖时）。两路结果按四边形 IoU>0.3 去重合并。
2. **分辨率策略**：**不复用 OCR 缩放图**（§1.5）。位图用原图；PDF 单独渲染 200dpi 起、必要时 300dpi；若原图最长边 >5000 则分块（tile 2048–3072，重叠 15%），分块检测后合并。
3. **几何**：zxing 默认开 `try_rotate/try_downscale/try_invert`；cv2 侧对不理想场景做 0.5×/0.75×/1.5×/2× 多尺度 + 反色（`255-img`）各跑一次（成本可控，见性能预算）。
4. **1D 码**：只接受长度/类型合理的命中（EAN/UPC 校验位、Code128 长度≤80 等），降低误检；对检测到但解码失败的 1D 区域：若 `zxing` 返回 `valid=False/error`（`return_errors=True`）且结构与 1D 相似，按"疑似条码"仍打码（`status="pending"` 或直接 black，视 D2/D3）。
5. **不依赖 OCR**：码检测独立于文本 OCR；OCR 不可用时也照常检出（现有 image/tiff verify 在 OCR 不可用时 `checked=0`，必须由码检测补上）。
6. **总开关/参数**：`YINZHAN_BARCODE_MODE=off|detect|mask`（默认 mask）、`YINZHAN_BARCODE_DPI=200`、`YINZHAN_BARCODE_MAX_TILES=…` 便于性能与故障回退。

### 4.3 打码绘制规范

| 项 | 规范 | 依据 |
|---|---|---|
| 覆盖形状 | 用返回的四边形（quad）做 `cv2.fillPoly` **实心填充**，不是 bbox 模糊/马赛克 | DESIGN.md:238-258 明确"图片=高斯模糊/马赛克"是错误做法 |
| 颜色 | 与前端涂黑一致 `INK=(13,11,9)`（`image_parser.py:24`）；灰度图填 0 | 主题一致性 |
| 外扩 | **静区外扩**：QR 每边 ≥4 模块；1D 每边 ≥10 模块（EAN/UPC 左 11/右 7，取更大值）；额外加 1–2px 抗锯齿保险 | 防止 edge 像素残留、重编码后重新可读 |
| 模块宽度估算 | QR：`min(quad 边长) / 模块数`（由 `format/version` 或解码成功后的 `ec_level/format` 推算；失败时按 `min_edge/25` 保守）；1D：按条码高度的一半或 `payload` 长度估算；无法估算时按边长 3% 外扩兜底 | — |
| 多码 | 每个 quad 单独填；相交/相邻的合并成一个框（避免黑色缝隙里残留边缘） | — |
| Office/PDF | PDF 用 `add_redact_annot(rect, fill=(0,0,0)) + apply_redactions()`；DOCX/XLSX 用 zip 级替换 media 为黑图（§4.5） | 实验 B.5 |
| 不改变页面其他内容 | 除 quad+静区外不扩大涂黑范围；打码后必须重新编码（JPEG q92 保持现有 `_save_image` 逻辑） | `image_parser.py:341-357` |

### 4.5 PDF 打码细节（实验已验证）

1. 渲染页 200dpi（扫描页已渲染 OCR 图可复用；文本层页需新增一次渲染，约 80–150ms/页）。
2. 像素 quad → 页面 pt：`pt = px * 72 / dpi`，并按页面旋转矩阵处理（现有 `_to_pdf_space`，`pdf_parser.py:93-98`）。
3. `page.add_redact_annot(rect, fill=(0,0,0))`；由于 PyMuPDF 对 quad 取外接矩形，**旋转码建议直接用外接矩形**（多涂一点可接受，符合"宁多勿漏"）。
4. `page.apply_redactions()` 默认 `images=PDF_REDACT_IMAGE_PIXELS`：被覆盖的图像像素会被涂黑；**部分覆盖同一张图也有效**（实验 B.5：照片角落的二维码，覆盖整码或覆盖一半都不可再解码，控制组可解）。
5. 之后照旧 `set_metadata({}) / del_xml_metadata() / save(garbage=4)`（`pdf_parser.py:615-624`）。
6. 备选：整页栅格化再涂黑（能覆盖矢量/特殊编码，但会丢文本层、体积变大）→ 作为 D8 决策点，默认不用。

### 4.6 Office 内嵌图片细节（P1）

- DOCX：`word/media/*` 是普通图片部件；把命中图替换为同尺寸纯黑 PNG（保留 mime 与 rels），zip 重打包即可；注意：**不要**把 `word/media` 从包中删除（会破坏 rels），只替换内容。
- XLSX：`xl/media/*`；openpyxl round-trip 后媒体仍在（实测 `xl/media/image1.png` 保留），所以"先用 openpyxl 完成文字脱敏导出，再 zip 级替换 media"是可行路径；如果图片带透明/裁剪，替换为同尺寸黑图即可（外形由 drawing 锚点决定，不改布局）。
- 若媒体检测失败但图片存在：导出前必须告警并进入"人工复核"阻断（安全默认，见 D5）。
- P0 可以先做**"检测 + 告警 + 可选强制整图涂黑"**，避免"能看见码但不管"。

### 4.7 Verify 扩展（硬门）

在 `pipeline.verify`（`pipeline.py:511-552`）新增码类检查：

1. **重新检测**：对成品按格式重跑检测（图片/TIFF 直接读帧；PDF 渲染 200dpi；DOCX/XLSX 解包 media）；
2. **硬指标**：成品上任何引擎**成功解码出非空 payload → 直接 `VerifyError`**（"导出后仍可解码"）。这是与用户"打码"语义最直接的判据；
3. **软指标**：导出前检测到的每个码位置，在成品的对应位置应有足够大的涂黑覆盖（像素黑占比 >95%），否则告警/失败（防"只涂了一半"）；
4. **计数守恒**：成品上"检测到 quad 但解码失败"的数量不得明显多于导出前（说明可能是新码/漏检），差异写 warning 供人工复核；
5. OCR 不可用时也必须跑码 Verify（补上现有 `checked=0` 的空白，见 B.3）。

> 注意：现有 `verify` 是"重新 parse 成品"（`pipeline.py:518-521`）；码类检查不能依赖重 parse 的文本，必须独立走图像检测。

### 4.8 UI / 工作流（仅描述，不改代码）

- 对照台出现 `二维码/条形码` 条目（默认 accepted + 涂黑），可逐条查看/取消（取消需二次确认，并提示"码内容可能含敏感信息"）。
- 解码内容默认**不显示原文**，只显示类型/长度/格式（如 `QR · 78 字符`）；"查看内容"需显式点击且不写入审计/日志（CONTRACT.md:230-236 审计只记类型与数量）。
- 若某码无法解码：仍然打码，并在清单里标注"未解码（已涂黑）"。
- 导出前摘要增加一行："二维码/条码：检出 N 处，全部涂黑；成品复检不可解码 ✓"。

### 6.2 指标（建议写进本批验收）

| 指标 | 目标 | 判定方式 |
|---|---|---|
| 检测召回（合成集） | QR ≥99%，2D 其他 ≥98%，1D ≥95% | 与标注 quad 的 IoU>0.5 判命中 |
| 检测召回（真实样例） | ≥95% | 人工标注 |
| **导出后不可解码率** | **100%**（硬门） | 成品用 zxing+cv2 双引擎重跑，任何非空 payload 即失败 |
| 打码覆盖率 | 覆盖 quad+静区，码区域黑像素占比 >95% | 像素统计 |
| 误检 | 无码页误检 ≤2 页/100 页；误检可人工取消 | 样例集 |
| 性能 | 200dpi ≤120ms/页；300dpi ≤250ms/页；42 页扫描 PDF 增量 ≤8s | 计时 |
| 回归 | 现有 5 个 e2e 样例（README:275-285）全过；原有 OCR 文本召回不下降 | e2e.py |
| 安全 | 无网络请求；审计不落码内容；临时文件任务结束清理 | 静态检查 + 抓包/审计抽查 |

## 7. 风险与边界

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **漏检导致误发**（低分辨率、反光、折叠、残缺码、非常规码制） | 高危：码随图外发 | 高召回参数（多尺度/反色/300dpi）+ 默认全打 + Verify 硬门 + 导出前摘要 + 用户人工复核；说明"不能保证 100%" |
| R2 | 打码过大影响可读性（外扩静区/合并相邻码/PDF redaction 取外接矩形） | 中：文档观感 | quad 精确 + 按模块宽度算静区；合并仅相邻；PDF 旋转码接受少量多涂（决策 D8） |
| R3 | 误检（表格线、密集文字被当成 1D 码） | 中：过度打码 | 1D 增加校验位/长度/结构过滤；`status=pending` 可人工取消；量化误检指标 |
| R4 | 依赖/打包：zxingcpp 是 C++ 扩展，PyInstaller 可能漏收 | 中：桌面版缺引擎 | `collect_all("zxingcpp")` + 打包自检（导入 + 解一个码）；wheel 入离线包；失败降级 cv2 |
| R5 | 离线安装：现场无网、wheel 版本不匹配（cp312/abi3） | 中 | deploy 内置 wheel；`pip install --no-index` 文档；CI 里做干净 venv 安装测试 |
| R6 | 解码内容二次泄露（日志/审计/前端） | 高：审计成新泄露源 | 审计只记类型/数量（CONTRACT.md:230-236）；payload 仅内存/界面显式查看；不写 `doc.warnings` |
| R7 | PDF 矢量绘制的码、特殊编码/加密 PDF | 中 | 渲染图检测已覆盖矢量（渲染后是像素）；加密 PDF 现有逻辑已拒绝；特殊编码列入 P3 兜底（整页栅格化） |
| R8 | 现有 Verify 在 OCR 不可用时 `checked=0`，形同虚设 | 高：安全假象 | 码 Verify 独立于 OCR；同时建议把"OCR 不可用 → verify 降级"改成显式 warning/阻断（另议） |
| R9 | 性能：文本层 PDF 需额外渲染 200–300dpi | 低 | 实测 80–150ms/页；可先 200dpi；取消/超时保护 |
| R10 | EXIF 方向、CMYK/16bit/透明 PNG、超大图 | 中 | P0 做 EXIF transpose + 格式归一；超大图分块；CMYK/P 图先转 RGB |
| R11 | 合规话术：打码 ≠ 合规 | 中 | README 已明确"已隐去"不等于"已合规"（README:247-260），新增码能力沿用该口径 |

## 8. 待审核决策点

| # | 决策点 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| **D1** | 是否引入 zxing-cpp 作为主引擎 | ①引入（+cv2 兜底）②只用 cv2 | **①** | 实测覆盖/1D/鲁棒性差距明显；Apache-2.0、wheel≈1MB、离线可行 |
| **D2** | 是否"默认一律打码、不做内容判断" | ①是 ②解码后按内容决定 | **①** | 码语义不可靠判敏；遮挡/低对比解码失败仍必须打；漏打后果远大于多打 |
| **D3** | 1D 商品条码是否白名单例外（EAN/UPC 商品码可能不敏感） | ①默认也打，后续按需白名单 ②现在就不打 | **①** | 先保守；白名单做成可选配置（后续版本再放开），避免默认漏打 |
| **D4** | 解码结果用途 | ①仅审计类型/数量 + 界面可选查看 ②不保留任何解码信息 ③写入审计 | **①** | 满足"可审计、可提示"，同时不制造二次泄露源 |
| **D5** | DOCX/XLSX 内嵌图片在 P0 的处理 | ①检测+告警+导出前阻断/二次确认，P1 自动处理 ②P0 直接静默跳过 | **①** | 契约要求"不能静默丢弃"（CONTRACT.md:143-148）；安全默认 |
| **D6** | 是否保留 cv2 作为第二意见（双引擎） | ①保留（成本低）②只 zxing | **①** | cv2 已在依赖里；双引擎交集/并集提高召回，成本仅兜底时触发 |
| **D7** | 检测分辨率/性能参数 | ①200dpi 起、300dpi 兜底、分块 ②统一 150dpi 省时 ③统一 300dpi | **①** | 150dpi 实测丢 2/8 QR；300dpi 全页 148ms 可接受 |
| **D8** | PDF 打码方式 | ①redaction（矩形外接）②整页栅格化 ③只覆盖不 redaction | **①** | 真删除内容、保留文本层、实测不可解码；栅格化仅在特殊编码时兜底 |
| **D9** | 是否处理 EXIF 方向 | ①P0 处理（推荐）②P1 | **①** | 手机拍摄件是最常见入口，方向错会显著漏检 |
| **D10** | 契约显式化：`VisualMark` 复用 vs 新增 `Document.barcodes` | ①P0 复用 visual_marks，P1 视需要再升格 ②一开始就改契约 | **①** | 少改契约、导出链路零改动、可快速交付；后续有需要再正式化 |
