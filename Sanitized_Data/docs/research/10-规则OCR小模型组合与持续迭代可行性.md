# 10 · 规则包 + OCR + 小模型：产品形态与持续迭代可行性

> **状态**：调研稿（可行性判断 + 架构建议 + 路线估算）· 2026-10-20
> **问题**：我们已有一套脱敏规则和 OCR 套件，能否把它们与「DeepSeek 小模型」组合进产品？客户资料脱敏不理想时，小模型能否持续迭代？
> **边界**：本批**只新增调研文档，不改任何代码/规则/依赖**。文中所有"建议"都需先过 [red-lines.md](../red-lines.md) 的门禁，尤其是 S2（引擎零外呼）与 S8（话术诚实）。
> **读者**：产品、工程、算法、法务、销售。
> **口径**：模型规模/许可证/价格均为 2026-10-20 检索到的公开信息；显存与延迟为**估算**，未在本机实测。带「推断」的条目不当事实使用。

## 0 一页结论

| # | 问题 | 结论 | 详见 |
|---|---|---|---|
| 1 | 规则 + OCR + 小模型能不能组合进现有产品？ | **能，而且工程接入点已经现成**：规则包 YAML 热加载、`Detector` 插件契约、`mediascan` 视觉扫描、`pipeline.verify` 出口复检都是可扩展的。缺的不是接入点，而是**模型包管理、评测集、反馈数据链**。 | §2、§4 |
| 2 | 「DeepSeek 小模型」适合做现场识别吗？ | **不建议**。截至 2026-10，DeepSeek **没有官方小参数模型，也没有官方微调服务**；API 只有 `deepseek-flash`（V4.1-Flash-1017 档）与 `deepseek-v4-pro`，开放权重最小主力也是 284B/13B 激活级。DeepSeek 适合放在**机构版的"重文档理解/难例复核/蒸馏教师"**位，不适合桌面默认路径。 | §3 |
| 3 | 客户资料脱敏不理想时，小模型能不能持续迭代？ | **能，但要拆成三条回路**：规则/词典（小时级，现场可做）→ 专用小模型（周/月级，离线模型包）→ 大模型/OCR 文档理解（季度，机构版）。所谓"客户现场自学习"不能做，也不该承诺。 | §5 |
| 4 | 产品形态怎么卖？ | 个人版（¥199/年）**不要拿"AI"当涨价理由**；增值点在机构版（¥3.88 万/年起）、行业规则/模型订阅、定制训练与评测服务。模型是能力底座，**卖的是"效果可验收 + 持续变好"**。 | §6 |
| 5 | 值不值得现在做？ | **值得，但顺序要对**：先做 P0 评测集与归因（1–2 人周），确认"不理想"到底有多少是模型能解决的；再上 0.1–0.6B 专用 PII 小模型做"候选器"（4–6 人周）；最后才是 DeepSeek OCR/VLM 的机构版能力（10–15 人周）。**总投入约 25–35 人周**（不含法务/销售）。 | §8 |

**一句话**：可行，但不是"把 DeepSeek 小模型塞进脱敏软件"，而是把产品从"规则 + OCR 工具"升级成**"规则保底 + 专用小模型召回 + 评测闭环 + 离线更新包"的识别平台**；DeepSeek 在机构版承担重文档理解与教师模型，现场迭代靠签名更新包（规则/模型），而不是在线学习。

**两个先验数据**（决定选型）：① 通用 PII 小模型在英文榜很强、中文很弱——OpenAI Privacy Filter AI4Privacy span F1 0.855（Presidio 0.431 / GLiNER 0.577），但**中文仅 0.138**、系统性偏召回（P 0.31–0.54 / R 0.70–0.85），只能当召回层；② 小模型微调确实有效——tw-PII-bench 零样本 54.1% → 微调 86.0%，但 Pioneer Agent 的教训是"朴素重训掉 43 分"，**评测集与回归门禁是前提**。

## 1 问题拆解：不是"塞一个模型"，而是"四层分工 + 三条回路 + 三档部署"

### 1.1 四层分工（先想清楚模型该坐哪一层）

| 层 | 职责 | 现产品对应 | 建议载体 | 迭代速度 | 主要风险 |
|---|---|---|---|---|---|
| **L0 规则/校验器** | 格式确定、可校验的敏感项：身份证/银行卡/统一社会信用代码/单证号/金额/表头列 | 已成熟：8 包 103 条规则 + 校验器 | 保持不变，**永远是权威层** | 小时–天（YAML 热加载） | 长尾格式漏、规则误报 |
| **L1 专用小模型** | 规则覆盖不到的**语义型 PII**：人名/机构名/地址/上下文推断的账号、非标准写法 | `ner_det.py` 目前是**启发式**（无模型） | 0.1–0.6B token-classification（ONNX/CPU） | 周–月（模型包） | 漏检/误报、边界切分、中文域偏移 |
| **L2 OCR/视觉** | 把扫描件变文本、把图里的目标找出来：人脸/证件/印章/二维码/版面 | PP-OCRv6 small（CPU 2.1s/页）+ `mediascan` 视觉扫描 | 保持 CPU 方案；机构版可加 GPU OCR/VLM | 季度（引擎版本） | OCR 错字传导、手写/低清、版面还原 |
| **L3 生成式大模型/VLM** | 复杂版面理解、手写/表格、疑难上下文判定、难例复核、教师 | 无（红线 S2 禁止外呼） | **仅机构版/私有云/离线批处理**；DeepSeek-OCR-2 或 V4.1-Flash 视算力 | 季度–半年 | 幻觉、成本、合规、不可解释 |

> 关键判断：**L1 才是"小模型持续迭代"的主战场**；L3 是机构版的能力上限，不是桌面版的默认路径。把 L3 塞进个人版，会同时输掉算力账、隐私账和毛利账。

### 1.2 三条迭代回路（回答"持续迭代"到底迭代什么）

| 回路 | 迭代对象 | 数据来源 | 交付方式 | 周期 | 适用客户 |
|---|---|---|---|---|---|
| **A 规则回路** | 正则/词典/校验器/表头列/替换策略 | 现场"框选补漏"、拒绝/改判、误报日志（仅类型+上下文，本地） | 规则包热加载 + 签名离线更新 | 小时–天 | 全部 |
| **B 小模型回路** | 通用 PII 小模型 / 行业 adapter / 客户 adapter | 公共数据 + 合成数据 + 客户**授权后的脱敏样本包** | ONNX 模型包（签名/版本/回滚） | 周–月 | 专业版/团队版/机构版 |
| **C 大模型/文档理解回路** | OCR/VLM 的版面、表格、手写；疑难判定 prompt/agent | 机构版难例集、脱敏后样本 | 引擎大版本 / GPU 一体机镜像 | 季度–半年 | 机构版 |

### 1.3 三档部署（同一套模型能力，按算力分档交付）

| 档位 | 目标客户 | 算力 | L1 模型规模 | L3 是否可用 | 单价锚点（09 报告） |
|---|---|---|---|---|---|
| **桌面个人/专业版** | 律师/医生/财务个人 | 普通 CPU，无外呼 | 0.1–0.6B INT8（几百 MB） | ❌（做"脱敏后云侧质检"可选，见 §5.5） | ¥199–499/年 |
| **团队版** | 小律所/诊所/财务团队 | CPU 为主，可选出 GPU 小卡 | 同上 + 行业 adapter | ⚠️ 可选（客户自有 API/Graph 卡） | ¥1,999/年（5 席） |
| **机构版/一体机** | 医院/律所/企业内网/测绘 | 内网 GPU（8–24GB 起） | 0.6–3B 专用模型 | ✅ DeepSeek-OCR-2 / V4.1-Flash 等 | ¥3.88 万/年起 + 订阅 |

> 三档共用**同一套模型包格式、评测集、签名与回滚机制**，避免"个人版一套、机构版一套"的维护分裂。

## 2 现状盘点：底座比想象中更接近，缺口不在模型

### 2.1 已经具备的（来自仓库与红线基线）

| 能力 | 现状 | 对"接模型"的意义 |
|---|---|---|
| 规则包 | 8 包 **103 条**自有规则（common/finance/legal/medical/geo/trade/pipl/table），YAML 热加载、include、优先级、同值合并 | 规则是最快迭代回路，**不用等模型** |
| OCR | rapidocr 自带 **PP-OCRv6 small**，6 核 CPU 约 **2.1s/页**，离线、无外呼 | 桌面版 OCR 基线够用；L1 模型不需要 GPU |
| 检测器插件 | `Detector` 契约 + `registry.register_detector`；`detect: [{type: regex|joined_regex|dict|ner|table_column|numeric_cell}]` | 新增 `model_ner` 类型即可接入，**不用改管线** |
| 视觉扫描 | `mediascan.register_scanner` + `visual_targets`（人脸/证件/车牌）+ `barcodes` | 图像类模型/算法有统一入口 |
| 出口自检 | `pipeline.verify`：重跑检测器 + 元数据 + 视觉/码类残留，失败即删成品 | **模型检测必须接入 verify，否则"漏了也报 0 残留"** |
| 离线商业化 | 机器码 + Ed25519 离线授权、免费版配额、价格页（设计稿） | 模型包可复用同一套签名/离线更新思路 |
| 安全红线 | S2 引擎零外呼；S8 不承诺"合规/匿名化" | **云 API 处理原文直接违规**；产品话术必须收着说 |

### 2.2 还缺的（真正要补的底座）

1. **评测集与指标**：没有按行业/实体类型的 golden set，也没有 recall/precision/每页耗时基线 → 现在说"脱敏不理想"是主观的，模型迭代会变成盲调。
2. **模型包管理**：没有模型目录、manifest、签名、版本、灰度、回滚；PyInstaller 打包体积与离线安装也要设计。
3. **反馈数据链**：`/api/jobs/{id}/mark`（框选补漏）、`accept/reject` 已经产生高质量信号，但没有落成"样本库 → 评测/训练"的格式；审计按红线不记原值，需要另建**加密、本地、最小化**的样本存储。
4. **Verify 的模型复检**：目前 verify 重跑规则与视觉/码类，**不重跑模型**。若模型参与检测，verify 必须能重跑模型（或至少对模型候选区做二次校验），否则会产生新的"假安全"。
5. **算力分档**：桌面 CPU 只能跑 INT8 小模型；GPU 路径（OCR-2/VLM）在机构版才成立。

### 2.3 先归因："脱敏不理想"不全是模型问题

| 归因 | 典型表现 | 模型能解决吗 | 优先手段 |
|---|---|---|---|
| 规则没覆盖 | 新格式单证号、方言地址、行业黑话 | ⚠️ 部分（L1 可补语义） | 先补规则（回路 A），再考虑模型 |
| OCR 读错/没读出 | 手写、低清、印章遮挡、竖排 | ⚠️ 部分（L2 OCR/VLM） | 换 OCR/VLM 比换 NER 更有效 |
| 语义型 PII | 人名/机构/上下文隐含的客户名单 | ✅ 是 L1 的主场 | L1 小模型 + 人工确认 |
| 规则太宽误报 | 把普通词当人名、金额过度打码 | ✅ 部分（L1 判上下文） | 阈值/否定词典 + 模型判别 |
| 替换/导出问题 | 金额勾稽破坏、格式错乱、Excel 公式 | ❌ 模型无关 | 已有专项方案（04/05） |
| 性能/体验 | 扫描件慢、批量卡 | ❌ 模型只会更慢 | 异步/分块/缓存 |

> **建议先做 2 周归因**：拿 20–50 份真实"不理想"样例逐条标错误类型，产出一张"错误类型 × 占比 × 可解决手段"表。没有这张表，任何模型选型都是拍脑袋。

## 3 模型选型：DeepSeek 能做什么、不能做什么

### 3.1 DeepSeek 公开矩阵（2026-10-20）

| 类别 | 模型 | 规模/许可 | 对本产品的意义 |
|---|---|---|---|
| API | `deepseek-flash`（V4.1-Flash-1017） | 552B 级 MoE（模型卡口径：prefill 8B / decode 16B 激活）、1M 上下文、原生图像输入、MIT | **云侧可用**，但 API 与"零外呼"冲突；只能做脱敏后质检/离线教师（见 §5.5） |
| API | `deepseek-v4-pro` | 1.6T 总参 / 49B 激活，纯文本，MIT | 同上，更贵更重 |
| 开放权重 | V4-Flash / V4-Pro | 284B / 13B 激活；1.6T / 49B，MIT，FP8/FP4 | 机构版"私有云/离线批处理"可用，但需要多卡服务器 |
| 开放权重 | V3.2 / V3.1 / V3 / R1 | 671B / 37B 激活；V3.1/V3.2/V4/R1 为 MIT，**V3 初版权重为 DeepSeek 自定义许可（OpenRAIL 衍生，含用途限制）** | 逐模型卡核对许可证；自定义许可需保留声明并做用途自查 |
| 蒸馏小模型 | R1-Distill **1.5B / 7B / 8B / 14B / 32B / 70B** | MIT，Qwen2/Llama3 底座，**2025-01 后未再更新** | 唯一能"单卡甚至 CPU 微调"的 DeepSeek 系小模型，但它是**推理模型**，不是抽取器；做 PII 需要额外改造 |
| OCR/VLM | DeepSeek-OCR **3.34B**（MIT）/ **OCR-2 3.39B**（Apache-2.0） | 仅提供 CUDA/flash-attn 路径；Q4 量化后约 2.5GB 显存（估算），实用需 8–16GB GPU | 机构版"版面复杂/需 markdown 结构化"时替换 PP-OCR 的候选 |
| 旧小模型 | V2-Lite 16B/2.4B 激活、Janus-Pro 1B/7B | 自定义许可 / MIT | 许可与能力都不理想，不建议作为底座 |

**三个硬事实**（决定选型）：

1. **DeepSeek 没有官方"小模型"产品线**，2026 年也没有新发布小模型；能拿来微调的只有 2025 年初的蒸馏系列。
2. **DeepSeek 没有官方微调/托管训练服务**（API 文档只有推理与 Agent 接入）；开放权重可自建微调：ms-swift 支持 V4 LoRA（示例 8 卡）/全参（64 卡），Modal 案例 64×H200。**现场不具备这个算力**。
3. **DeepSeek-OCR-2 是 GPU 模型**，不是桌面 CPU 方案；对"扫描件 OCR 精度"有提升，但对"人名/机构语义"没有直接帮助。

> 补一句最容易被误解的：**你现在对话的 `deepseek-flash` 就是上述云端 API 模型（V4.1-Flash 档），不是能打进安装包的"小模型"**。它可以做规则建议、评测集生成、难例归因等"不接触原文/只接触脱敏后数据"的辅助工作，但不能作为客户本地的识别引擎。

### 3.2 更适合"现场可迭代"的小模型（L1 候选）

| 模型 | 规模 | 许可证 | 中文 | CPU 可行 | 适配点评 |
|---|---|---|---|---|---|
| **OpenMed-PII-Chinese** 系列 | 135M / 278M / 568M / 600M | Apache-2.0 | ✅ 中文专用 | ✅ ONNX INT8（官方有 CPU/Android/浏览器版本） | 54–55 类标签、F1≈0.74–0.76（合成+AI4Privacy 测试集，**不能当真实基线**）；512 token 上限，需分块；临床域偏多，需按行业再微调 |
| **GLiNER-PII**（Knowledgator） | Qwen3-0.6B | Apache-2.0 | ⚠️ 多语但中文未验证 | ✅ 0.6B 可 CPU（较慢） | 零样本标签可配、支持流式；英文 F2≈90.5，多语平均 F2≈68.2，法律多语场景更弱 |
| **GLiNER2-PII**（205M） | 205M | Apache-2.0 | ❌ 七种欧洲语言 | ✅ | 更轻，但中文不支持，只能参考架构 |
| **OpenAI Privacy Filter** | 1.5B 总参 / 50M 激活 MoE | Apache-2.0 | ❌ 中文仅 **0.138**（公开评测） | ✅ 浏览器/笔记本可跑，官方有 Transformers.js | AI4Privacy span F1 **0.855**（同榜 Presidio 0.431、GLiNER 0.577）；但**偏召回**（P 0.31–0.54 / R 0.70–0.85）、人名仅 0.40、中文/阿拉伯文很差 → **只能做召回层，不能单独交付** |
| **Presidio**（对照，非候选） | 规则/词典框架 | MIT | ❌ 默认基本无效 | ✅ | 内置实体无中国、上下文词英文、中文 `\b` 失效；要用必须自写身份证/手机号识别器 + 校验位 `validate_result` 杀误报——**正好证明规则层不能丢** |
| **Piiranha** | mDeBERTa-v3-base | **CC-BY-NC-ND-4.0** | ❌ 六种欧洲语言 | ✅ | **许可证禁止商用/演绎**，按红线不得引入；仅作对照 |
| **Qwen3.5 小模型**（0.8B/2B/4B/9B） | 0.8B–9B | Apache-2.0 | ✅ 较好 | ⚠️ 0.8B–2B 可 CPU（慢），4B+ 建议 GPU | 通用底座，可做"上下文判定/难例复核"；需要微调成抽取任务，不是开箱即用 |
| **PaddleOCR PP-OCRv6 small** | 现有 | Apache-2.0 | ✅ | ✅ 2.1s/页 | **不要动**，它是桌面 OCR 的性价比基线（新版见 §3.3） |

> **许可证纪律**（与红线 §三.4 一致）：只引入 MIT / BSD / Apache-2.0 / PSF；`Piiranha` 的 CC-BY-NC-ND 直接排除；`DeepSeek-V2-Lite`、`DeepSeek-VL2` 是自定义许可，要单独评审。
>
> **两个反例值得记住**：① **Presidio 默认对中文基本无效**（内置实体无中国、上下文词是英文、中文 `\b` 失效），中文落地必须自写身份证/手机号识别器并用校验位杀误报——**规则层不是"旧技术"，而是精度层**；② **OpenAI Privacy Filter 的"跨榜第一"是英文榜**（AI4Privacy span F1 0.855），中文仅 0.138、且系统性偏召回，不能拿英文 F1 当卖点，也不能直接放进中文产品。
>
> GLiNER2-PII（205M、42 类、7 语、Apache-2.0）在 SPY 风格评测 F1 **0.477 > OPF 0.380**，但精度仅 0.35–0.37，官方建议加词典/阈值压误报——这正是"模型召回 + 规则精度"的级联思路；中文场景可看 OpenMed 568M（ONNX INT8、纯 CPU、55+ 类）。

### 3.3 OCR/版面：CPU 档够用，VLM 只在结构还原

- **桌面 CPU 继续用 PP-OCRv6 small**（现有 2.1s/页基线）。PP-OCRv6（2026-06）三档 tiny/small/server 参数约 **1.5M / 7.7M / 34.5M**，较 v5 检测 +4.6%、识别 +5.1%，OpenVINO CPU 端到端约 **5.2×**——"纯 CPU"卖点守得住；表格/版面优先 PP-StructureV3。
- **跨页表、公式、阅读顺序才需要 VLM/文档解析大模型**：PaddleOCR-VL-1.6（0.9B，OmniDocBench 96.3%）、MinerU 4.0（默认 ONNX CPU、四档质量）、DeepSeek-OCR（3B MoE，约 100 vision token/页，单 A100 约 20 万页/天）、olmOCR 7B（<$200/百万页，需 12GB+ 显存）。
- **olmOCR-Bench 参考排序**：PaddleOCR-VL 80.0 > DeepSeek-OCR 75.7 > MinerU 75.2。注意这是通用 benchmark，**必须用自己的文档类型实测**，不能直接选型。
- **结论**：先换 OCR/版面，再谈换 NER 模型——扫描件漏检里"OCR 错字/版面丢失"的占比，通常高于"人名识别误差"。

### 3.4 选型结论

- **桌面版（L1）**：优先 **OpenMed-PII-Chinese 278M/568M（ONNX INT8）** 做候选器；用自有行业标注微调；GLiNER-PII 作为"标签可配"的备选。**不要放≥3B 模型**。英文通用模型（如 OpenAI Privacy Filter）中文实测仅 0.138，**必须自建/微调 + 中文评测**，不能直接拿英文榜第一当卖点。
- **机构版（L2/L3）**：PP-OCRv6 保底；复杂版面/表格/手写先试 **PaddleOCR-VL-1.6（0.9B）** 或 **MinerU 4.0（ONNX CPU）**，需要更强视觉/私有云再上 **DeepSeek-OCR-2（3.39B，Apache-2.0）**；疑难语义/文档级判断用 **DeepSeek-V4.1-Flash / V4-Flash（MIT）** 或 Qwen3.5-VL，放私有云/一体机，**不出内网**。
- **DeepSeek 蒸馏小模型**：只在"要一个可本地微调的通用小底座"时考虑，且需评估其推理模型特性；不作为首选。
- **OpenAI Privacy Filter**：架构与产品形态值得学（1.5B/50M 激活、浏览器可跑、可微调、明确声明"不是匿名化"），但中文标签体系需重训，不能直接商用落地。

## 4 目标架构：规则保底、模型召回、评测闭环

### 4.1 总体架构（建议）

```
文档 ──▶ 解析/版面 ──▶ OCR(PP-OCRv6, 本地) ──▶ 文本 + 坐标 + 版面
                              │
                              ├─ L0 规则包（正则/校验位/词典/表头列）──▶ 高置信实体
                              ├─ L1 小模型（PII token 分类, ONNX INT8）──▶ 候选实体 + 置信度
                              ├─ L2 视觉/码类（人脸/证件/印章/二维码）──▶ 图像实体
                              └─ L3 大模型/VLM（仅机构版, GPU）──▶ 版面/疑难候选（可选）
                                              │
                                    融合层（规则权威 + 模型候选 + 冲突标记）
                                              │
                              人工确认（低置信/待确认/框选补漏）
                                              │
                                  替换/涂黑（现有 replacer）
                                              │
                          Verify（规则重跑 + 模型重跑 + 视觉/码类/元数据）
                                              │
                                           导出
```

### 4.2 融合原则（五条，写进 CONTRACT）

1. **模型只出候选，规则/策略做决策**：模型输出 `(span, type, confidence, source)`，不直接改写文档；高风险类型仍由规则/人工确认。
2. **宁可误报、不可漏报，但误报要可拒绝**：低置信进"待确认"，高置信才自动处理；L3 敏感类（身份证/银行卡/人脸）保持"规则命中即处理"的确定性。
3. **冲突显式化**：规则命中但模型判"非敏感"、模型高置信但规则不认，都标 `conflict`，交人工；不得静默取其一。
4. **verify 必须重跑模型**：模型参与检测后，`pipeline.verify` 增加"模型复检"路径（同模型/同阈值重跑成品文本；或对模型候选区做二次校验），否则模型漏检会变成"残留 0"的假安全。
5. **可解释与审计**：每个实体记录 `origin`（rule/model/manual）、模型版本、阈值；审计不记原值（红线 S5）。

### 4.3 接入点（按现有契约，尽量少改核心）

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增检测器 | `app/server/yinzhan/detectors/model_ner_det.py` | 实现 `Detector` 契约；`from_spec` 读 `model_id/threshold/device/labels`；`detect()` 返回 `Entity`（含 `confidence`、`origin="model"`）|
| 规则包扩展 | `rules/*.yaml` | 新增 `detect: [{type: model_ner, model: pii-cn-278m-v1, threshold: 0.5, labels: [...]}]`；**规则格式向后兼容**，旧包不受影响 |
| 模型包管理 | 新模块 `yinzhan/modelpack.py` | `models/<model_id>/<version>/` + `manifest.json`（sha256、license、labels、metrics、min_app_version、device、signature）；启动时校验；缺失时降级为纯规则 |
| 进程隔离 | 独立子进程/本地 stdio | 模型推理放子进程，崩溃不拖垮引擎；只读加载；无网络；CPU/GPU 由 manifest 声明 |
| Verify 扩展 | `pipeline.verify` | 增加 `model_residual`：成品重解析后跑同模型，残留不通过则删除成品 |
| 视觉扫描 | `mediascan.register_scanner` | OCR/VLM 版面识别（若机构版）复用该入口，输出 `ScanHit` |
| 状态/开关 | `jobs` + `YINZHAN_ML=0/1`、`YINZHAN_ML_DEVICE=cpu/cuda`、`YINZHAN_ML_THRESHOLD` | 默认关闭；Pro/机构版按授权开启；免费版不加载模型（控制体积与速度） |
| 体积与打包 | `desktop/app.spec` + 安装包 | 小模型 100–600MB：建议**按需下载/离线模型包**，安装包不默认全带；机构版单独分发 |

> 注意：`detect` 契约、`Entity` 字段、`verify` 签名都属 CONTRACT 范畴；按红线 §三.6，**先改 CONTRACT.md，再改实现**。

### 4.4 评测体系（没有它，迭代就是盲调）

| 项 | 建议 |
|---|---|
| 评测集 | 每行业 100–300 份**真实授权**样例（脱敏前用于评测、不外传），按实体类型分层；另建 20–50 份"当前漏检/误报"难例集 |
| 指标 | 实体级 recall / precision / F2（召回优先）；页面级漏检率；每页新增耗时；误报条/份；OCR 传导误差 |
| 门槛 | 高敏类（L3）**漏检率不高于现有基线**才允许上线；整体 recall 提升 ≥ 5 个百分点、误报不恶化；桌面新增耗时 ≤ 0.5s/页（目标） |
| 回归 | 每次规则/模型更新跑固定回归集；版本冻结；线上灰度 A/B；回滚包 |
| 诚实口径 | 不承诺 100% 召回；不承诺"合规/匿名化"（红线 S8）；对外只写"已隐去/去标识化 + 辅助识别" |

## 5 持续迭代：三条回路怎么落地

### 5.1 回路 A：规则/词典（最快、最便宜、最该先做）

- **数据**：`/api/jobs/{id}/mark`（框选补漏）、`/api/jobs/{id}/entities/{eid}`（accept/reject）、审计类型统计。
- **做法**：离线"规则建议器"——从漏检 spans 生成候选正则/关键词/校验器草案；人工审核后进规则包；**不自动上线**（防误报扩散）。
- **交付**：签名规则包（可离线导入），热加载；小时–天级。
- **价值**：客户今天抱怨的问题，可能 60% 靠规则补丁解决；先做这个，模型只补剩余长尾。

### 5.2 回路 B：专用小模型（周–月级）

| 环节 | 建议做法 |
|---|---|
| 数据来源 | ① 公共/合成数据（AI4Privacy、中文合成证件号/手机号）；② 厂商自有行业样例；③ **客户授权后的脱敏样本包**（默认不外传，见 §5.5） |
| 标注 | 实体级 span + type + 边界；从"框选补漏/拒绝"半自动转标注，人工复核；每轮 500–2,000 条即可起量 |
| 训练 | 0.1–0.6B encoder 全参微调（单卡 4090/24GB 足够）；或 LoRA；CPU 侧只推理不训练 |
| 评测 | 过 §4.4 门槛；与现有规则做**并集/冲突分析**，避免"模型把规则已命中的又报一遍" |
| 发布 | 模型包：`model_id` + 版本 + 标签表 + 指标 + sha256 + Ed25519 签名 + 兼容 app 版本；灰度 5%→50%→100%；保留回滚 |
| 防遗忘 | 通用数据 + 行业数据 + 客户数据混合；客户专属用 adapter 分离，**不为每个客户 fork 主模型**（维护地狱） |

**微调收益与门槛（公开证据，值得写进立项材料）**

- **收益明确**：tw-PII-bench 上 OpenAI Privacy Filter 零样本 54.1% → 本地微调 **86.0%**；OPF 论文给出交叉点：英文合成约 500 条、医疗约 1,000 条即可超过零样本。
- **但评测集是刚需**：Pioneer Agent（2026-04）用线上失败样本 + 回归约束重训，实体 F1 0.345→**0.810**；**朴素重训反而掉 43 分**。没有固定评测集和回归门禁，微调会负收益。
- **主动学习有成熟实践**：不确定性采样 + 人工修正条数作为质量门，先自动覆盖 80%+ 再人工复核（US12182307B1 等专利实践）。
- **成熟产品的级联范式**：Microsoft Purview SIT = 正则 + 校验 + 关键词 + 邻近度 + 置信度分档（65/75/85）+ ML 命名实体，并用 Match/Not a Match 反馈调优——**和我们建议的"规则保底 + 模型召回 + 置信度路由 + 反馈"同构**。
- **结论**：每个行业准备 **500–1,000 条高质量标注**即可起步；但**评测集必须先于训练集存在**。

### 5.3 回路 C：大模型/文档理解（季度级，机构版）

- **OCR 升级**：复杂版面/表格/手写 → 先试 **PaddleOCR-VL-1.6（0.9B，OmniDocBench 96.3%）** 或 **MinerU 4.0（默认 ONNX CPU）**，需要更强视觉理解/私有云再上 **DeepSeek-OCR-2（3.39B，Apache-2.0，GPU）** 或 Qwen3.5-VL；先做 A/B，确认对"漏检率"有真实提升再替换（olmOCR-Bench 参考：PaddleOCR-VL 80.0 > DeepSeek-OCR 75.7 > MinerU 75.2）。
- **疑难判定**：DeepSeek-V4.1-Flash / V4-Flash（MIT）做"上下文歧义/文档级判断/难例复核"，输出结构化候选；只允许在机构内网/私有云，禁止原文出域。
- **教师模型**：用大模型对**已脱敏/合成**样本打标 → 蒸馏到 L1 小模型，降低对人工标注的依赖；这是"DeepSeek 最合理的角色"。
- **成本**：GPU 一体机（硬件+维保）或私有云；按项目报价，不进入个人版成本结构。

### 5.4 客户"现场持续迭代"的四种交付方式

| 方式 | 数据出域 | 算力 | 效果上限 | 交付周期 | 合规/风险 | 建议 |
|---|---|---|---|---|---|---|
| ① 现场规则/词典更新 | 否 | 无 | 中（格式/词典类） | 小时–天 | 低 | **立刻做** |
| ② 样本包回传 + 厂商训练 | **是**（需授权+脱敏+最小化） | 厂商侧 | 高（语义/长尾） | 1–3 周/轮 | 中（PIPL/合同/审计） | **推荐作为主线** |
| ③ 机构版本地微调工具 | 否 | 客户 GPU | 中高（客户专属） | 2–4 周 | 低（数据不出域），但客户要有算法能力 | 大客户可选 |
| ④ 联邦学习 | 否 | 客户 + 厂商 | 中（工程复杂） | 月+ | 低但重 | **暂缓**（客户量不够时不划算） |

> 结论：**"小模型持续迭代"在产品上应表现为"模型包订阅 + 可选样本回传 + 评测报告"，而不是"软件自己越用越聪明"。** 后者在离线产品里既做不到，也不该承诺。

### 5.5 合规与红线（必须先定；以下为研究稿，需法务复核）

> **本产品最大的合规风险不是"识别效果"，而是"用了客户数据训练模型"这一步**：一旦把客户样本用于改进自有模型，厂商就从"受托人"变成"独立个人信息处理者"，需要自建合法性基础。因此默认策略必须是：**本地不联网、默认不回传、回传只给脱敏标签/统计特征**。

#### 5.5.1 角色与法律关系

| 场景 | 厂商角色 | 法律依据 | 必须先具备 |
|---|---|---|---|
| 纯本地软件（数据处理全在客户机器/内网，厂商不接触原文） | 工具提供者/受托人 | PIPL 第 21、59 条；《网络数据安全管理条例》第 12 条 | 委托/许可合同明确目的、方式、范围；不访问、不留存、不关联分析的书面承诺；处理记录留存 ≥3 年 |
| 客户主动回传**脱敏样本**用于模型改进 | **独立处理者**（去标识化不改变个人信息属性，向厂商"提供"须单独同意） | PIPL 第 23 条；含敏感信息另需第 29 条 | 单独同意 + 告知 + PIA（第 55/56 条，报告留存 ≥3 年）+ 数据最小化 + 可撤回 |
| 厂商聚合多客户数据自训 | **独立处理者** | 《数据安全法》第 21、30 条；《生成式AI暂行办法》第 7 条第 3 项、第 8 条；《条例》第 19 条 | 逐户授权 + PIA + 重要数据评估 + 标注规则与质量评估 + 训练数据安全管理 |
| 客户本地训练（客户自己的 GPU/数据，厂商只给工具） | 工具提供者 | 参照《条例》第 16 条 | 不访问、不留存、不关联分析；工具本身不联网 |

> **"去标识化 ≠ 匿名化"**（PIPL 第 73 条第 3、4 项）：去标识化后仍属个人信息，需要第 13 条合法性基础；除非通过重标识测试（可参照 **GB/T 42460-2023《个人信息去标识化效果评估指南》**），否则对外**不得称"匿名化/合规"**——这与红线 S8 完全一致。注意：GB/T 35273-2020 中"共享去标识化信息可免告知同意"的表述早于 PIPL，**不能作为免责依据**。

#### 5.5.2 训练/微调三条路径（风险递增）

| 路径 | 数据出域 | 风险 | 建议 |
|---|---|---|---|
| ① 客户本地训练（数据不出域） | 否 | **最低** | 机构版大客户首选；厂商只交付训练工具+评测脚本，书面承诺不访问数据 |
| ② 脱敏样本回传 → 厂商训练 | 是 | **中高**（仍属个人信息，须第 23 条单独同意） | 推荐作为"效果迭代"主线，但必须独立开关 + 单独同意 + PIA + 样本白名单 + 可撤回 |
| ③ 厂商聚合多客户数据自训 | 是 | **最高**（独立处理者 + 重要数据评估） | 早期不做；确需做时逐户授权并出 PIA 报告 |
| ④ 合成数据/差分隐私（推荐补充） | 否 | 低 | 优先用合成数据起量，减少对客户原文的依赖 |

> 《生成式AI暂行办法》第 7 条第 3 项要求训练数据涉个人信息"取得同意或符合法定其他情形"，第 8 条要求标注规则与质量评估；《条例》第 19 条要求训练数据及处理活动安全管理。**"样本回传自训"是最大风险点，必须与"委托处理"切割并单独授权。**

#### 5.5.3 备案与标识

- **《生成式AI暂行办法》**：仅规范"向境内公众提供"；第 3 款明确企业研发应用**未向公众提供的不适用**——单客户私有化部署原则上无需大模型备案，但合同须**禁止客户对外经营**。
- **算法备案/安全评估**：具舆论属性或社会动员能力者，按《算法推荐规定》第 24、27 条做安全评估+算法备案。
- **《深度合成规定》第 19 条第 2 款**：技术支持者"参照"备案——若产品含文本改写/生成并向多客户交付，有被认定为"技术支持者"的风险（**各地网信执行口径不一，建议书面沟通**）。
- **《人工智能生成合成内容标识办法》（2025-09-01 施行）**：若含生成功能，第 4、5、9 条要求显式标识 + 元数据隐式标识；不添加显式标识须留存日志 ≥6 个月。
- **境外 API**：另涉数据出境与《办法》第 20 条处置风险；本产品定位"本地/境内"，不建议引入境外 API。
- **开源许可证**：逐仓库核对 LICENSE 与 LICENSE-MODEL。DeepSeek-R1 为 MIT；**DeepSeek-V3 权重适用 DeepSeek License Agreement（OpenRAIL 衍生，含"不得用于完全自动化决策损害个人合法权利"等用途限制）**；V4/OCR-2 分别为 MIT/Apache-2.0，但仍需保留声明并做用途自查。

#### 5.5.4 行业红线（机构版落地前由法务出清单）

| 行业 | 关键要求 |
|---|---|
| **金融** | JR/T 0171-2020：个人金融信息分 C3/C2/C1；**未去标识化脱敏不得交第三方处理；C3 及鉴别辅助信息不得委托**；数据库不得外部运维；委托须做安全影响评估并监督（JR/T 0197-2020 为分级指南） |
| **医疗** | 《人口健康信息管理办法（试行）》第 10 条**禁止境外存储/托管**、第 11 条委托方担责且受托方禁超权限、第 16 条等保、第 18 条痕迹可追溯；《电子病历应用管理规范（试行）》第 14/16 条须保存历次操作印痕，第 19 条保存 15/30 年 |
| **测绘/地理** | 《测绘法》及自然资发〔2020〕95 号设绝密/机密/秘密三级；涉密成果不得擅自复制转让；处理涉密数据须**涉密资质与涉密系统审批**；地图成果另需审核；精度阈值见附件目录（未逐项核对） |
| **律所** | 《律师法》第 41 条保密义务（国家秘密、商业秘密、当事人隐私）、第 52/53 条罚则；外包须客户同意 + 保密协议 |
| **通用** | 等保（《网络安全法》第 21 条、GB/T 22239-2019）、《数据安全法》第 27 条、新修《网络安全法》第 20 条（AI 安全监管，2026-01-01 施行）；金融/医疗客户常以合同要求 SM2/3/4 国产密码支持（密评 GB/T 39786-2021 对 CII 强制） |

#### 5.5.5 产品必须准备的合规证据链（9 项）

1. **定位与边界说明**：本地处理、不联网、不留存、默认不外发（与 README/红线一致）。
2. **角色矩阵 + DPA/委托协议**：禁转委托、审计权、删除销毁、≥3 年记录。
3. **单独同意与告知模板**（样本回传、敏感信息场景）。
4. **PIPIA 与重要数据风险评估模板**（报告留存 ≥3 年）。
5. **数据来源授权台账、标注规则、回传白名单**。
6. **模型版本留痕**：版本号、数据清单、训练/评测日志、模型卡（对应 §5.2 模型包 manifest）。
7. **不可篡改审计日志 + 定期合规审计**（PIPL 第 54 条、《条例》第 27 条）。
8. **备案判断清单**：公众/舆论属性/深度合成标识/技术支持者身份。
9. **开源与出口合规清单**：许可证、用途限制、境外依赖。

> 机制底线：**默认"本地训练或只回传脱敏标签/统计特征"；回传原文必须独立开关 + 单独同意 + PIA；升级包签名可回滚；上线前做重标识测试并出报告。** 这与 §2 的 S2 零外呼红线并不冲突——云 API 只能作为"脱敏后数据"的独立产品线，不能进桌面引擎。

### 6.2 商业化建议（与 09 定价对齐）

- **个人版不靠模型**：¥199 的价格带覆盖不了 GPU 成本，模型只做"轻量本地小模型"且默认关；卖点仍是"本地、可还原、跨格式、专业规则"。
- **机构版才是模型变现点**：¥3.88 万/年起 + **规则/模型订阅**（如 ¥0.8–1.5 万/年）+ **定制训练/评测服务**（按行业 3–8 万/次）+ 维保。模型让"机构版"有持续付费理由。
- **不要按"模型能力"单独定价个人版**：用户买的是"省时间 + 免担心"（09 报告结论），不是参数量。
- **卖"效果诊断/复盘"服务**：机构版首年做一次"错误类型归因 + 评测报告"，之后按季度出"漏检改善报告"——这是把"持续迭代"变成可验收交付的关键，也是年费续约的抓手。
- **可验收指标写进合同**：不承诺 100% 召回，但承诺"漏检率不高于基线 + 每季度模型/规则更新 + 疑难样本 48h 响应"。

### 6.3 竞争格局与壁垒

- **国内头部已"AI 化"**：绿盟（含亿赛通）2025 中国 DLP 份额 **18.5% 第一**（IDC 2026-06），公开材料称用大模型做摘要/分类分级/按行业样本自动生成检测规则再复核，叠加 OCR + 图像指纹；达观推"曹植"一体机；深信服 XDLP 公开承认传统正则 DLP"告警海量、误报多、易绕过、图纸照片难识别"；合合 TextIn 支持本地化（100 页 1.5 秒、50+ 语言）。
- **海外计费四类**：按人（Purview 独立版约 $12/用户/月 + 扫描量；Nightfall 按用户/年 + 数据包）、按扫描量（Macie 每 GB、Google 按字节）、按数据源订阅（BigID 可自托管、Cyera 仅云）、按一体机/项目（国内主流）。**Nightfall 已出 MCP 网关与 Claude Code hooks**——"给 Agent 的前置脱敏门"是真实赛道，和我们的 MCP 方向一致。
- **判断**：律所/医疗/测绘"数据不出域"是硬约束，SaaS 难切入；**本地一体机 + 年度模型/规则订阅 + 按席位或文档量**更可行（国内报价多为项目制、未公开，不确定）。
- **我们的差异化**（模型是商品，壁垒不在模型）：① 8 包 103 条行业规则 + 校验器（精度层）；② 离线/零外呼/可审计的信任状；③ 文档级"真删除 / 可还原换名 / 跨格式"；④ 行业评测集与反馈闭环；⑤ **可解释的规则订阅**（客户能看懂"为什么遮"）。
- 因此：**模型要接，但别把公司叙事变成"我们做模型"**；应讲"规则 + 小模型 + 评测闭环，越用越准（通过更新包）"。

## 7 风险与对策

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | 模型漏检/幻觉 | 信任崩塌（比误报严重得多） | 模型只做候选；规则/人工兜底；高敏类保持规则权威；verify 重跑模型；不承诺 100% |
| 2 | 误报上升 | 用户逐条拒绝，效率反而下降 | 置信度阈值 + 待确认队列 + 误报预算；评测门槛卡"误报不恶化" |
| 3 | 评测集缺失/过拟合 | "离线指标涨、线上效果不涨" | 每行业 golden set + 盲测 + 版本冻结 + A/B |
| 4 | 客户数据回传违规 | 法律/声誉风险 | 默认不回传；授权+PIA+最小化+可撤回；样本包人工确认 |
| 5 | 桌面体积/性能 | 安装包暴涨、OCR 更慢 | 模型按需/按版本分发；INT8；子进程；异步；免费版不加载 |
| 6 | 版本漂移/回滚失败 | 客户现场无法恢复 | 模型/规则版本与 app 兼容矩阵；签名；灰度；一键回滚 |
| 7 | 许可证踩雷 | 商用侵权 | 只允许 MIT/BSD/Apache-2.0/PSF；Piiranha 类 NC-ND 直接排除；V2-Lite/VL2 自定义许可单独评审 |
| 8 | 把"持续迭代"承诺成自动学习 | 交付纠纷 | 对外说清"更新包 + 服务"，不说"自学习" |
| 9 | 组织能力不足 | 模型上线后无人维护 | 至少 0.5–1 人负责评测/标注/模型运维；先外包训练也可 |
| 10 | 云 API 破坏零外呼卖点 | 核心信任状受损 | 云只做"脱敏后质检"独立产品线；引擎代码保持无外呼 |

## 8 实施路线与工作量（建议，非承诺）

| 阶段 | 内容 | 交付/验收 | 估算 |
|---|---|---|---|
| **P0 归因与评测** | 20–50 份真实"不理想"样例归因；每行业 100–300 份评测集；指标与门槛；规则补丁清单 | 错误类型占比表；基线 recall/precision/耗时；首批规则补丁 | **1–2 人周** |
| **P1 L1 小模型 PoC** | OpenMed-PII-Chinese 278M/568M ONNX 接入；`model_ner` 检测器；verify 扩展；UI 置信度/待确认；默认关闭 | 在评测集上 recall 提升 ≥5pp、误报不恶化、桌面新增 ≤0.5s/页；回归全绿 | **4–6 人周** |
| **P2 反馈闭环与模型包** | 样本库（加密/本地/导出）；厂商侧微调流水线；模型包 manifest/签名/灰度/回滚；法律/医疗/财务行业包 | 一轮"客户反馈 → 模型更新 → 灰度 → 回滚"演练成功；机构版可交付 | **6–10 人周** |
| **P3 机构版文档理解** | GPU 一体机路径；DeepSeek-OCR-2 / V4.1-Flash（或 Qwen3.5-VL）接入；复杂版面/表格/手写；可选"脱敏后云侧质检" | OCR/版面漏检率对比报告；单页成本；私有化部署包 | **10–15 人周** |
| **合计** | 不含法务/销售/硬件采购 | | **约 25–35 人周** |

**硬约束（来自公开实践）**：① 模型上线前必须先有固定评测集与回归门禁——Pioneer Agent 的教训是"朴素重训掉 43 分"；② 每行业 500–1,000 条高质量标注即可起步（OPF 论文的交叉点），但标注人/验收人必须先到位；③ 模型包与规则包都要签名 + 可回滚，否则机构客户不敢用。

**建议顺序**：P0 → P1 → P2 → P3。**不要反着来**（先买 GPU/先训模型，通常会把钱花在"模型能解决但业务不痛"的地方）。

### 决策点（需拍板）

| # | 决策 | 推荐 |
|---|---|---|
| D1 | 首个付费行业/客户（律所/医疗/财务/贸易/测绘） | 选"规则覆盖最全 + 样本最多"的行业先做，别五个一起上 |

## 9 直接回答

| 维度 | 判断 | 理由 |
|---|---|---|
| **技术可行性** | **高** | 插件架构现成；0.1–0.6B PII 小模型 CPU 可跑；OCR 基线已有；缺的是评测/模型包/反馈链，都是工程问题 |
| **产品可行性** | **中高** | 分档交付可行；但"持续迭代"必须产品化为更新包+订阅+服务，不能承诺自动学习 |
| **商业可行性** | **中** | 个人版价格带养不起模型；机构版（3.88 万/年起 + 订阅）是变现点；模型是差异化不是独立卖点 |
| **合规可行性** | **中** | 本地/零外呼天然占优；风险集中在"客户数据训练"和"云 API"；需授权、PIA、话术克制 |

**给决策者的三句话**：

1. **能做，而且你们的基础比多数同行好**——规则、OCR、插件、离线授权、出口自检都在，接模型是"加一层"而不是"重做一遍"。
2. **别把 DeepSeek 小模型放进桌面默认路径**——官方没有小模型、没有微调服务，V4 级模型现场跑不动；桌面用 0.1–0.6B 专用 PII 模型，DeepSeek 放机构版做 OCR/VLM/教师。
3. **先做评测与规则迭代（2 周），再上小模型（4–6 周）**；把"持续迭代"做成"离线签名更新包 + 可选样本回传 + 评测报告"，这才是能卖、能交付、能合规的形态。
